# 意图确认细则

## 1. 探索（详细、只读）

**先推词义和产物。** 复述前先写一句「这个说法通常指什么东西」，再定形态和范围。例：只要「只读现状图」就不要做成「改库表 / 可编辑数据模型」；服务清单默认是「目标服务 + 它的直接依赖」，不是全机房。说法和现有代码结构对不上时，按词义做，不硬套现有数据模型。

**读资料的顺序（固定）：**

1. 用户原话、对话上下文、已有 `wizard/intent.md`。
2. 工作区的 `CLAUDE.md` / `AGENTS.md` / `README`。
3. 被描述或被改动对象自己的 README、compose、部署文件（依赖关系通常就写在这里）。
4. `tasks/` 下的历史任务（含归档）。
5. 要改的代码。
6. 最后才是更大范围的台账（设备清单、全量服务表、远端机器）。

前面几类没读完，不得把其中能查到的内容当成未知、写成假设或拿去问用户。

**范围默认：目标加它的直接依赖。** 再远的上下游不进来，无关的服务不进来。派摸底 subagent 时把这个范围写进交代，并要求每条结论带出处（文件:行或命令）。

要摸清的上下文：

- **现状**：相关代码 / 配置 / 文档的现状与入口；现在怎么工作、哪里不满足。
- **约束**：技术约束、接口与兼容性、时间或资源限制、用户原话里的禁止项。
- **已有工作**：`tasks/` 下相关任务与 ADR、近期提交、已有方案或失败尝试。
- **歧义**：原话里哪些词有多种读法、哪种读法会改变做法。

面广时可并行派只读 subagent 分头摸（交代目标、输入、只读、详情落 `evidence/intent/<主题>.md`），只回简短摘要（结论 + 证据路径 + 未决）。主会话不转贴全文。

## 2. 覆盖清单（内部用，不照着打印）

复述前自查这几项都想清楚了；它们写进 `wizard/intent.md`（见第 6 节），**不**逐项打印给用户：

要干嘛（含为什么）· 怎么干 · 输出什么（含做完的样子、落在哪）· 上下文（现状、约束、已有工作）· 不做 · 我的假设 · 我的决定（歧义按推荐定下，带一句理由）· 需要你提供的（只限真阻塞）

## 3. 给用户的复述（自然口语）

- 1–3 句话，第一人称，像同事口头确认：自然带出做什么、怎么做、产出什么、落在哪。
- 上下文、假设、不做的事：只在会影响结果时顺带一句，不用就不提。
- 结尾说接下来会发生什么（如「写完告诉你放在哪」）。
- 说决定、不提问：见 taskrail [user-report.md](../../taskrail/references/user-report.md)；歧义按推荐说成决定并带理由。
- 不要标题、不要加粗标签、不要逐字段列出。

示例：

- 好，我按仓库的约定挑个合适的位置写成一份文档，内容包括流程图、各 skill 的分工、两种模式、两个档位的区别和怎么用，并在 README 和 taskrail 里加链接。写完告诉你放在哪。
- 我先查清导出慢在查询还是文件生成，再优化最慢那段，用 1 万行报表对比，目标是 5 秒内导出且内容不变；我先按只管网页端来做，报表格式不动。改完把前后耗时发给你。
- 我把登录失败的提示统一成一处处理，顺手补上错误码测试；这次先只改网页端，App 端等网页端稳定后再跟，免得两端一起回归。改完把测试结果发你。
- 我先把页面和节点、连线的数据结构做好，各存一张表，后面要改字段得迁数据，所以先说一声。这次先不做初始数据导入，服务你后面自己加，免得跟还没修好的导入链路绑在一起。做完把页面地址发你。

## 4. 纠偏（human）

- 复述本身就是确认请求；用户指出不对时，用同样的口语重述改过的部分。
- 用户指出遗漏或错误（如「X 呢？」）：先回第 1 节的一手资料重查，再用陈述句说改了什么、出处在哪，例如「补上了服务 B 和 C，服务 A 的 compose 里写着它依赖这两个」；不提问，不再凭猜补一版。
- 用户显出困惑或不满（如「你搞得我都不自信了」）：立刻停止提问，查清后直接给有出处的结论。
- 只重述被指出的部分；被纠正过的同一处不得再错；纠正与原话冲突时以最新纠正为准。
- 多轮仍有分歧：把两种理解并排写清，并写明我按哪种做、为什么；仍不收敛按 taskrail [user-report.md](../../taskrail/references/user-report.md) 第 5 节「卡住」停，说明需要用户用自己的话描述目标。
- 用户没回话不算确认。

## 5. 代审（goal）与审查清单

goal 不问人：按 taskrail [confirm-protocol.md](../../taskrail/references/confirm-protocol.md)「另一个模型审」派审（派法与派不出的处理只在那里），随附用户原话、复述、探索摘要，按下面清单审。

审查清单（P0 / P1 挡路，P2 不挡）：

1. P0 **添目标**：复述里有原话和摸底都推不出的目标或范围。
2. P0 **漏约束**：原话里的限制 / 禁止 / 期限没进「不做」或「做完的样子」。
3. P0 **自加限制或缩窄**：「不做」里有原话推不出的限制，或把宽泛目标缩小了，且没标成假设。
4. P0 **形态不符词义**：说法的通常含义与复述的产物形态对不上（如「只读图」被做成「改库表」）。
5. P0 **该查没查**：能从一手资料查到的内容被写成假设、未知或拿去问用户（指出能回答它的文件）。
6. P1 **不可检查**：「做完的样子」两个独立执行者会判出不同结论。
7. P1 **范围失当**：漏了目标的直接依赖，或扩进无关范围。
8. P1 **上下文不撑做法 / 假设失当**：做法违反已知约束；会改范围的假设没标「把握低」。

不审：文风、实现方案是否最优、需求本身是否合理。

无 P0 / P1 即通过；不过就修订再审，最多两轮，仍不过则剩余发现写进「我的假设」，`status: assumed`，继续推进。意图涉及线上、不可逆或对外发送时照常确认意图；这些动作本身执行前按 user-report 第 5 节停。

## 6. `wizard/intent.md`

```markdown
---
status: confirmed | assumed
reviewer: <human | 模型名>
---
<给用户的那段口语复述，原样>

## 覆盖清单
- 要干嘛：<目标>；为什么：<…>
- 怎么干：<思路与关键步骤>
- 输出什么：<交付物、落点>；做完的样子：<可检查标准>
- 上下文：现状 <…>；约束 <…>；已有工作 <…>（证据：evidence/intent/…）
- 不做：<…>
- 我的假设：<…（把握高/低）>
- 我的决定：<歧义按推荐定下 + 一句理由；难回头的标「难回头」；同步追加到 `TASK.md`「已做决定」；没有写「无」>
- 需要你提供的：<只限真阻塞：缺了做不下去且只有用户能给；没有写「无」>

## 纠偏记录
- <改了什么，一句话>
```

意图中途变更时直接改写本文件并在纠偏记录追加一行（git 可追溯旧版），流程见 taskrail 契约「意图变更」。

## 7. 结构化示例（`wizard/intent.md` 的覆盖清单）

用户原话：「把导出功能弄快点」；给用户的复述即第 3 节第二条示例。

```markdown
## 覆盖清单
- 要干嘛：让「导出报表」从点击到下载更快；为什么：大报表要等很久
- 怎么干：定位慢点（查询 / 文件生成）→ 优化最慢一段 → 1 万行报表前后对比
- 输出什么：优化后的导出接口；做完的样子：1 万行导出 ≤5 秒（现约 40 秒），内容不变
- 上下文：现状 同步执行、整表查询；约束 不改报表格式；已有工作 上月加过索引（证据：evidence/intent/current.md）
- 不做：不改报表格式，不加新导出类型
- 我的假设：慢在查询（把握低）；只管网页端（把握高）
- 我的决定：先只优化最慢那段，另一段不动，免得改动面变大
- 需要你提供的：无
```
