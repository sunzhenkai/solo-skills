# 评审协议（约束 / 预加载 / 输出骨架 / 角色边界）

原 constraints、preload-protocol、brief-protocol、role-vocabulary 四个文件合并于此，内容未改。

## 约束（原 constraints.md）

<!-- 原标题：核心约束 -->

`role-based-reviewer` 的共享约束、命令边界、角色协作与结尾巴块。

### 核心约束

- **只读**：不修改业务代码、不创建分支、不提交、不写文档/规格；用户明确要求修复时再改
- **先过门禁**：未过 SKILL.md 三道门禁不得预加载、不得分角色审查
- **结论绑定路径**：findings MUST 绑定 `path:line` 或符号/调用关系，禁止悬空断言
- **不确定就标出来**：不编造问题凑数；没有问题就明说没有
- **不越界**：不审查目标范围外的文件，除非它是理解目标所必需的上下文
- **用户要求实现/固化/提案时**：只给角色化上下文与下一步建议，引导到现有执行 skill（见下表），本 skill 不代做

### 命令边界

| | engineer | algo | data | sre | ops | biz | product | design | qa | skill |
|---|---|---|---|---|---|---|---|---|---|---|
| 视角 | 在线实现、性能、调用链 | 模型/策略/实验 | 管道、数仓、口径 | 集群、监控、发布 | 业务配置、灰度、运营流程 | 对外对接、多租户 | 需求与 spec | 交互流程、可用性、无障碍、状态覆盖、微文案、视觉一致性 | 可测性与回归 | 触发面、协议一致性、可执行性 |
| 典型下游 | `task-explore`、`taskflow`、`service-manager` | `task-explore`、`taskflow` | `task-explore`、`taskflow` | `service-manager`、部署/CI 相关约定 | 运营手册 / 配置变更流程 | 协议/对接文档 | `task-explore`、`taskflow`、OpenSpec（若项目有） | `task-explore`（design 阶段） | 测试与回归计划 | `skill-creator`、`skill-upgrader`（含 `evolve`） |
| 运行态上下文 | 按需 | 否 | 否 | 按需 | 按需 | 否 | 否 | 否 | 否 | 否 |
| 输出 | RoleBrief / 审查报告 | 同左 | 同左 | 同左 | 同左 | 同左 | 同左 | 同左 | 同左 | 同左 |

本 skill **不调用**其他 skill 的内部逻辑；在输出里写清「下一步建议执行哪个 skill」，由用户/主 agent 触发。项目里没有对应 skill 时，写清动作本身，不要编造不存在的 skill 名。

### 多角色协作

- `roles` 可指定 1 个或多个；未指定时默认 **engineer**，其它角色须强信号或用户确认（门 2）
- 每个角色保留独立证据与 findings，不得合并成无归属结论
- 共享对象按下方 redirect 与 「角色职责边界」节 的主问题归属定主责，其余为协作
- 下一步默认只选主责角色的一个动作；并行时拆任务并注明依赖
- 不为「让每个角色都有输出」而发明 findings（门 3）

### 角色间 redirect

命中边界时换视角，不要越权下结论：

| 边界 | 共享对象 | 判据 | redirect |
|------|---------|------|---------|
| intent ↔ product | 需求 / 意图 | 复述是否忠于用户原话 → intent；需求本身是否合理、值不值得做 → product | 互引 |
| sre ↔ ops | 灰度、配置 | 基础设施（集群/部署/配置下发/告警）→ sre；业务侧（功能开关/运营规则/渠道配置）→ ops | 互引 |
| sre ↔ engineer | 重启 / OOM / 稳定性 | 集群·部署·调度·探针 → sre；代码缺陷·GC·调用链 → engineer | 互引 |
| engineer ↔ algo | 推理 / 排序服务 | 可用性·性能·发版 → engineer；模型效果·策略·实验 → algo | 互引 |
| algo ↔ data | 特征 / 样本 / 模型分发 | 在线推理与效果 → algo；离线管道·样本质量·数仓分层 → data | 互引 |
| engineer ↔ data | 事件 / 追踪管道 | 在线可用性 → engineer；数据流与口径 → data | 互引 |
| ops ↔ engineer | 服务内业务开关、规则 | 配置/灰度/运营异常 → ops；代码缺陷 → engineer | 互引 |
| biz ↔ product | 需求 / spec | 消费 spec 做对接 → biz；产出 spec 做提案 → product | 互引 |
| biz ↔ engineer | 外部协议 vs 内部实现 | 合作方/多租户对接 → biz；内部服务实现 → engineer | 互引 |
| design ↔ product | 体验 | 视觉/交互/无障碍 → design；价值/范围/文案 → product | 互引 |
| design ↔ engineer | UI 落地 | 视觉与交互规格 → design；实现与性能 → engineer | 互引 |
| qa ↔ engineer | 测试 | 覆盖/回归/可测性 → qa；实现正确性 → engineer | 互引 |
| skill ↔ engineer | skill 内 `scripts/` | SKILL.md/references 的触发、协议与契约质量 → skill；scripts/ 代码缺陷 → engineer | 互引 |
| skill ↔ qa | 契约测试 | 正文承诺与 tests/ 断言的对应缺口 → skill；通用可测性与回归策略 → qa | 互引 |
| skill ↔ product | 存在价值 | skill 该不该存在、合并还是拆分 → product；已存在 skill 的质量诊断 → skill | 互引 |

### 结尾巴块

所有输出 MUST 在全文末尾追加 `### 总结与置信度`：

| 置信度 | 判据 |
|--------|------|
| 高 | 结论全部绑定明确路径，无 unknowns |
| 中 | 含 1–2 项 unknowns 或待验证项，主体已锚定 |
| 低 | 上下文不足，主要靠推断；建议缩小范围或补充材料 |

末尾 MUST 给出「下一步」（主责动作 / 是否需要运行态上下文 / 是否跨角色 redirect）。

## 预加载（原 preload-protocol.md）

<!-- 原标题：预加载协议 -->

按角色加载**当前仓库里实际存在**的上下文。路径不存在就跳过，不要编造或追逐死链。

### 通用层（所有角色）

按顺序尝试，命中即用；合计默认 ≤6 个文件（多角色去重后仍为此预算，超出 MUST 说明原因）：

1. **项目入口**：根 `README.md`、`AGENTS.md`（若有）
2. **规格/设计**：`openspec/specs/`、`docs/design/`、`docs/` 下与问题相关的索引或文档
3. **目标代码**：用户指定路径，或 `git diff` 中的核心文件（lockfile / 生成物 / vendor 不读）
4. **关联约定**：测试、调用方、配置样例——只读理解目标所必需的那几处

`mode=review` 先摸规模（`git diff --stat` / 文件清单），再决定读哪些；不要为求全打开几十个文件。未过门 1 时不要为了「可能要用角色视角」而预加载。

### 各角色优先锚点

「第一站」优先于盲读全库。按**生效角色**读取对应角色文件的「优先锚点」段：`references/roles/<role>.md`（`<role>` 为短名，如 `engineer`、`design`）。未生效的角色不加载其角色文件；锚点路径均为**示意模式**，以仓库里真实存在的文件为准。

### 运行态上下文

仅 engineer / sre / ops 在问题依赖环境时启用；其余角色省略。多角色请求中只收集一次，并只用于启用角色的结论。

来源（存在才读）：compose / Helm / K8s 清单、`.env.example`、项目内环境说明。只做摘要，不计入「为求全而堆文件」。涉及生产写操作时必须额外确认——本 skill 默认不执行写操作。

### 检索边界

- 需要广域代码检索时，先缩小到角色锚点与 diff 范围，再按需 grep
- 不要把本 skill 写成「全库扫描器」
- 外部仓库、未克隆路径、文档里的死链：标为 unknown，不假装已读

## 输出骨架（原 brief-protocol.md）

<!-- 原标题：输出骨架 -->

单角色用 RoleBrief；多角色或 `mode=review` 用聚合骨架，并保留每个角色的独立结论。骨架用于落盘与上游工作流；直接给用户看的摘要用口语转述（结论先行、术语白话），见 taskrail 契约「对用户说话」。

### RoleBrief（`mode=ask`）

```markdown
### RoleBrief

**角色**：<engineer / algo / data / sre / ops / biz / product / design（别名 uiux） / qa / skill>
**问题视角**：<用户问题的角色化重述，一句话>

#### 领域上下文
- 锚点：<本次实际读到的文件路径>
- 运行态：<仅 engineer / sre / ops 需要时填；其余省略>

#### 下游建议
- `<skill 或动作>` → <用途一句话>

#### 结论
- findings:
  - [path:line 或 符号 — 一行结论]

#### 下一步
- downstream：<主责动作>
- 跨角色协作：<主责 / 协作 / redirect；无则省略>

#### 总结与置信度
<高/中/低> — <一句原因>
```

### 聚合审查报告（`mode=review`，或多角色）

```markdown
### 审查范围
<目标与边界，一句话>

### 依据状态
<产物状态：<提交号 / dirty 摘要>（来源：<调用方提供 / 评审自取>）；审阅边界齐备性：<门包 / 画像 / 降级原文 / 运行态证据 / 审与不审——逐项标「齐」或缺哪一块>>

### 启用视角
<角色列表 + 推断依据>

### 总体结论
<通过 / 有条件通过 / 不通过 + 一句话理由；边界缺项时在结论后注明「覆盖度受限：<缺项>」>

### 分级发现
#### Blocker / Major
- F-1 [角色] 问题描述 — `path:line`，建议修法
#### Minor / Suggestion
- <默认省略；仅用户要求仔细审查时列出>

### 按角色结论
##### <角色>
- findings:
  - [path:line — 一行结论]
- 下游建议：`<skill 或动作>` → <用途>

### 跨角色 handoff
- 主责：<角色> — <理由>
- 协作：<角色> — <补充视角>
- 冲突或未知项：<无则明确写无>

### 未覆盖项与降级建议
<逐条：未覆盖条目 + 原因（信息不足 / 证据未提供 / 工具不可用）+ 建议处置（按调用方的「未覆盖即降级」登记，含 A/B 定级）；工具不可用时另写替代方法与能力边界>

### 下一步
- downstream：<主责的一个动作；并行时列明任务和顺序>

#### 总结与置信度
<高/中/低> — <一句原因>
```

### 字段约定

- **结论绑定**：每条 finding MUST 有 `path:line` 或符号/调用关系
- **状态绑定**：报告 MUST 在「依据状态」写明所审产物状态；换产物后受影响 findings 作废重审，不沿用旧结论
- **编号稳定**：Blocker / Major 按 `F-<n>` 编号且在同一轮内稳定；调用方以该编号登记处置（`fixed` / `accepted-recorded`），本 skill 不代记处置、不代判收敛
- **缺项不担保**：边界缺项（门包、运行态证据、参照集）时不得据此得出超越已审范围的结论；缺项写进「依据状态」并在结论后注明覆盖度受限
- **建议而非执行**：下游 skill 是建议；本 skill 不代为调用
- **简洁**：上下文已够就直接给结论，不必为填满模板而注水
- **去重**：跨角色同一风险只保留一条分级发现，并标明主责角色；视角明细里仍可各写各的关注点
- **无问题就说无**：不要为凑分级而发明 findings
- **默认不报毛刺**：Minor / Suggestion 受门 3 约束；风格、命名偏好、可选重构不进默认报告

## 角色职责边界（原 role-vocabulary.md）

**核心角色**：`engineer`、`product`、`design`、`qa`、`intent`（可推断或常用）。**可选角色**：`algo`、`data`、`sre`、`ops`、`biz`、`skill`——只在用户点名或调用方（如门包）传入时生效，不参与推断。

<!-- 原标题：角色职责边界 -->

可组合角色的职责、主问题归属与「我只管 X，不管 Y」。短名用于 `roles=`；`role-<name>` 只表示视角，不是独立 skill。

### 角色矩阵

| 短名 | 岗位 | 我管 | 我不管（交给） |
|------|------|------|----------------|
| `engineer` | 研发 | 架构落地、代码质量、错误处理、性能、并发、安全、可维护性、与现有约定一致 | 模型效果与策略（→ algo）；离线管道与口径（→ data）；集群调度（→ sre）；视觉规范（→ design） |
| `algo` | 算法 | 模型、排序/召回、策略、实验、在线效果 | 服务可用性/发版（→ engineer）；样本质量与数仓（→ data） |
| `data` | 数据 | 离线 ETL/数仓、特征与样本、模型分发管道、口径与归因 | 在线推理性能（→ algo）；在线排障（→ engineer） |
| `sre` | 运维 | 部署与回滚、配置与密钥、可观测性、资源与依赖、故障兜底 | 业务代码根因（→ engineer）；业务配置/灰度规则（→ ops） |
| `ops` | 业务运营 | 运营流程、业务配置、灰度与开关、手册与执行路径 | 集群/监控/基础设施（→ sre）；代码缺陷（→ engineer） |
| `biz` | 商务/对接 | 合作方接入、多租户、对外协议与落地消费 | 内部实现（→ engineer）；产出 spec（→ product） |
| `product` | 产品 | 需求覆盖、用户价值、边界与异常、交互闭环、文案、与既有行为一致 | 对接落地与代码实现（→ biz / engineer）；视觉细节（→ design） |
| `design`（别名 `uiux`） | UI/UX | 交互流程、可用性、无障碍、状态覆盖、微文案、视觉与设计系统一致性、响应式 | 后端逻辑（→ engineer）；需求范围与价值（→ product） |
| `qa` | QA | 可测性、覆盖缺口、边界/异常、回归、并发与时序、数据一致性 | 产品价值判断（→ product）；实现方案选型（→ engineer） |
| `skill` | Skill 诊断 | Agent Skill 的 description 触发面、门禁/协议一致性与可执行性、references 按需加载、契约测试覆盖、公开仓纪律 | `scripts/` 代码质量（→ engineer）；通用可测性（→ qa）；skill 存在价值（→ product） |
| `intent` | 意图复述审查 | 复述是否忠于用户原话：添加目标、漏掉约束、完成样子可检查、假设标注（仅调用方显式传入） | 需求合理性（→ product）；方案与实现（→ engineer） |

项目没有对应域时，不要强行启用 `algo` / `data` / `biz` / `ops` / `design`。目录或文件名沾边不是强信号；主体问题不在该角色职责内就不要加。

### 共享对象归属

同一模块按**主问题**归主责，不能只看目录名：

| 对象类型 | 可用性/性能/发版 | 效果/策略 | 数据/口径 | 体验 | 可测性 |
|---------|-----------------|----------|----------|------|--------|
| 在线服务代码 | **engineer** | — | — | — | qa |
| 推理 / 排序 | engineer | **algo** | — | — | qa |
| 模型分发 | — | algo（效果） | **data**（管道） | — | — |
| 特征 / 样本 | — | algo（质量） | **data**（管道） | — | — |
| 事件追踪 | engineer（在线） | — | **data**（流与口径） | — | — |
| 功能开关 / 运营规则 | — | — | — | — | — |
| 同上（配置语义） | — | — | — | ops 主责 | — |
| 同上（代码缺陷） | **engineer** | — | — | — | qa |
| 部署 / 重启 / 探针 | **sre** | — | — | — | — |
| UI 实现 | engineer | — | — | **design** | qa |
| 需求 / spec | — | — | — | product | — |

`功能开关`：配置语义与灰度节奏归 **ops**；开关代码缺陷归 **engineer**；下发通道与集群漂移归 **sre**。

### 组合规则

- `roles=` 只用短名；`uiux` 视为 `design`
- 各角色的优先锚点、核心检查清单、下游建议、跨角色 redirect 在 `references/roles/<role>.md`，仅角色生效时加载；本文件只管职责边界与归属
- 服务/目录名不能单独决定主责，必须按上表问题维度归属
- 多角色 review 中，表内加粗角色是风险 owner；其他命中角色只补充检查点与证据
- 未指定 `roles` 时默认 engineer；一次启用超过 2 个角色须用户确认（门 2）
