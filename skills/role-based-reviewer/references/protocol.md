# 评审协议（约束 / 预加载 / 输出骨架 / 角色边界）

## 约束

- 只读：不改业务代码、不建分支、不提交、不写文档 / 规格；用户明确要求修复时再改。
- 过了 SKILL.md 三道门才预加载、分角色审。
- 每条 finding 绑定 `path:line` 或符号 / 调用关系；拿不准就标「未验证」，没有问题就说没有。
- 用户要实现 / 固化 / 提案时，只给下一步建议，指向现有执行 skill（没有就写动作本身），由用户或主 agent 触发。
- 多角色时各角色保留独立证据与 findings；共享对象按下文定主责；下一步默认只给主责的一个动作。

## 预加载

只读仓库里实际存在的文件，不存在就跳过、标 unknown。合计默认 ≤6 个文件（多角色去重后同此预算，超出写明原因）：

1. 项目入口：根 `README.md`、`AGENTS.md`
2. 规格 / 设计：`openspec/specs/`、`docs/` 下与问题相关的文档
3. 目标代码：用户指定路径，或 `git diff` 的核心文件（跳过 lockfile / 生成物 / vendor）
4. 关联约定：理解目标必需的测试、调用方、配置样例（范围外文件只在此时读）

`mode=review` 先摸规模（`git diff --stat`）再决定读哪些；广域检索先缩到角色锚点与 diff 范围。生效角色读 `references/roles/<role>.md` 的「优先锚点」，锚点是示意模式，以仓库真实文件为准。运行态上下文（compose / Helm / K8s 清单、`.env.example`）只在 engineer / sre / ops 且问题依赖环境时读一次、只做摘要。

## 输出骨架

骨架用于落盘与上游工作流；给用户看的摘要用口语转述，见 taskrail `references/user-report.md`。没内容的段写「无」或省略。

`mode=ask`（单角色）写四行：问题视角、实际读到的锚点、结论（`path:line` — 一行）、下一步（主责动作或 redirect 给谁），末尾「总结与置信度」。

### 聚合审查报告（`mode=review`，或多角色）

```markdown
### 审查范围
<目标与边界，一句话>
### 依据状态
<提交号或未提交摘要（来源）；判据 / 运行态证据 / 参照 / 审与不审逐项标「齐」或缺项>
### 启用视角
<角色 + 推断依据>
### 总体结论
<通过 / 有条件通过 / 不通过 + 一句理由；边界缺项时注明「覆盖度受限：<缺项>」>
### 分级发现
- F-1 [角色] 问题 — `path:line`，建议修法
<Minor / Suggestion 仅在用户要求仔细审时列出>
### 主责与协作
<主责角色 + 理由；协作角色；冲突或未知项，无则写无>
### 未覆盖项
<条目 + 原因（信息不足 / 证据未提供 / 工具不可用，后者写替代方法）>
### 下一步
<主责的一个动作>
#### 总结与置信度
<高 / 中 / 低> — <一句原因>
```

置信度：高 = 全绑路径、无 unknown；中 = 1–2 项待验证；低 = 主要靠推断，建议缩范围或补材料。

- 报告只对「依据状态」里的产物有效；换产物后受影响的 findings 作废重审。
- Blocker / Major 按 `F-<n>` 编号，同一轮内稳定；调用方按编号登记处置（`fixed` / `accepted-recorded`），本 skill 不代记、不代判收敛。
- 边界缺项时，结论只覆盖已审范围。
- 跨角色同一风险只留一条分级发现，标主责角色。
- 风格、命名偏好、可选重构默认不报（门 3）。

## 角色职责边界

哪些角色可推断见 SKILL.md 门 2。`roles=` 只用短名，`uiux` 即 `design`；项目没有对应域时不启用。

| 短名 | 岗位 | 我管 |
|------|------|------|
| `engineer` | 研发 | 架构、代码质量、错误处理、性能、并发、安全、可维护性 |
| `algo` | 算法 | 模型、排序召回、策略、实验、在线效果 |
| `data` | 数据 | 离线 ETL / 数仓、特征样本、分发管道、口径 |
| `sre` | 运维 | 部署回滚、配置密钥、可观测性、资源依赖、故障兜底 |
| `ops` | 业务运营 | 运营流程、业务配置、灰度开关、手册 |
| `biz` | 商务对接 | 合作方接入、多租户、对外协议 |
| `product` | 产品 | 需求覆盖、用户价值、边界异常、交互闭环、文案 |
| `design` | UI/UX | 交互、可用性、无障碍、状态覆盖、视觉与设计系统一致、响应式 |
| `qa` | QA | 可测性、覆盖缺口、边界异常、回归、时序、数据一致性 |
| `skill` | Skill 诊断 | 触发面、协议一致与可执行、按需加载、契约测试、公开仓纪律 |

共享对象按主问题归主责（下表），不看目录名。各角色的锚点、检查清单、下游建议在 `references/roles/<role>.md`，仅角色生效时加载。

### 角色间 redirect

命中边界时按下表换视角：

| 边界 | 归属判据 |
|------|----------|
| sre ↔ ops | 集群 / 部署 / 配置下发 / 告警 → sre；功能开关 / 运营规则 → ops |
| sre ↔ engineer | 部署·调度·探针 → sre；代码缺陷·GC·调用链 → engineer |
| engineer ↔ algo | 可用性·性能·发版 → engineer；效果·策略·实验 → algo |
| algo ↔ data | 在线推理与效果 → algo；离线管道·样本·数仓 → data |
| engineer ↔ data | 在线可用性 → engineer；数据流与口径 → data |
| ops ↔ engineer | 配置 / 灰度 / 运营异常 → ops；代码缺陷 → engineer |
| biz ↔ product | 消费 spec 做对接 → biz；产出 spec → product |
| biz ↔ engineer | 合作方 / 多租户对接 → biz；内部实现 → engineer |
| design ↔ product | 视觉 / 交互 / 无障碍 → design；价值 / 范围 / 文案 → product |
| design ↔ engineer | 视觉与交互规格 → design；实现与性能 → engineer |
| qa ↔ engineer | 覆盖 / 回归 / 可测性 → qa；实现正确性 → engineer |
| skill ↔ engineer | SKILL.md / references 的触发与协议 → skill；`scripts/` 代码缺陷 → engineer |
| skill ↔ qa | 正文承诺与 tests/ 断言的缺口 → skill；通用可测性 → qa |
| skill ↔ product | 该不该存在、合并拆分 → product；已有 skill 的质量 → skill |
