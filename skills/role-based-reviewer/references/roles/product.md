# 产品（`product`）

角色文件：仅在本角色生效时加载（见 [preload-protocol](../preload-protocol.md)）；职责边界以 [role-vocabulary](../role-vocabulary.md) 为准。级别：🔴 Blocker / 🟡 Major（门 3 默认报）/ ⚪ 默认不报，拿不准降一级。`[运行态]` 条目纯 diff 评审降级为「⚠ 需运行态验证」。

## 优先锚点

需求、spec、概念/愿景、交互闭环。

跳过：代码实现、对接落地。

## 核心检查清单

每条附命中判据；判据不满足则不报。

1. 🟡 [代码] 需求闭环：主流程 + 异常/边界场景有明确行为定义，无「到时候再看」。
   命中判据：给出一个用户可达的场景（空态、失败、并发操作、权限不足），文档/代码都未定义系统该做什么。
2. 🟡 [代码] 与既有行为一致：不破坏既有用户习惯，术语与全局一致。
   命中判据：同一概念在改动前后或不同入口用了两个名字，或既有操作路径被无声改变且无迁移说明。
3. 🟡 [代码] 文案：用户可见文案明确、语气一致，无内部黑话外泄。
   命中判据：引用具体文案，指出普通用户无法理解（黑话/错误码直出）或与产品其余文案语气冲突。
4. 🟡 [代码] 可验收：每条需求有可验证的验收标准。
   命中判据：存在一条需求，无法回答「什么 observable 行为出现算这条做完了」。
5. 🟡 [代码] 范围显式：明确「不做什么」，无非目标时易被默认全做。
   命中判据：改动涉及的能力边界（支持的格式/规模/角色）在方案中无任何排除声明，且存在明显相邻能力会被误认为已支持。
6. ⚪ [代码] 价值与优先级论证：为什么现在做、服务谁。
7. ⚪ [运行态] 交互闭环实际走查（与 design 清单第 1 节互补，这里看业务结果是否达成）。

## 不算问题

- **「还能更好」的愿景**：超出本次范围的增强想法不报，最多作 Suggestion 并注明不阻塞。
- **实现方案选型**：用什么技术、什么库，归 engineer；product 只看行为定义与用户可见结果。
- **文案字数与排版口味**：语义明确、语气一致后，长短与措辞偏好不报。
- **小众边界场景穷举**：概率极低且不造成数据/金钱损失的边角，不列为闭环缺口。

## 跨角色 redirect

- biz ↔ product（需求/spec）：消费 spec 做对接 → biz；产出 spec 做提案 → product
- design ↔ product（体验）：视觉/交互/无障碍 → design；价值/范围/文案 → product
