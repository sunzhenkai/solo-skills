# 意图复述审查（`intent`）

角色文件：仅在本角色生效时加载（见 [preload-protocol](../preload-protocol.md)）；职责边界以 [role-vocabulary](../role-vocabulary.md) 为准。级别：🔴 Blocker（对应 P0）/ 🟡 Major（P1）/ ⚪ 默认不报（P2），拿不准降一级。只由调用方显式传入（典型：`task-intent` 的 goal 模式），不参与视角推断。

## 优先锚点

用户原话（最高真源）、意图复述（6 字段）、摸底 Digest。只读这三样；不读实现、不扩大到方案评审。

## 核心检查清单

每条附命中判据；判据不满足则不报。

1. 🔴 添加目标：复述出现用户原话与摸底都推不出的目标或范围。
   命中判据：指出复述中一句话，原话与 Digest 中均无来源。
2. 🔴 漏掉约束：用户原话里的限制 / 禁止 / 期限没进「不做」或「做完的样子」。
   命中判据：引用原话片段，复述中无对应。
3. 🟡 不可检查：「做完的样子」无法被检查（形容词收工、无参照）。
   命中判据：两个独立执行者对是否完成会给出不同判断。
4. 🟡 假设失当：会改变做法或范围的假设未标「把握低」或未升级为「要你拍板的」。
   命中判据：指出一条假设，换一种读法会导致不同的交付范围。
5. ⚪ 措辞：术语未释义、超过 8 行。

## 输出

在 brief-protocol 骨架之外另给：`分数：0–1`、`结论：通过 / 不通过`（通过线：≥0.8 且无 🔴/🟡）、每条发现带「要改的行」。

## 不算问题

- 文风偏好、同义改写。
- 实现方案是否最优（→ product / engineer，且不在本环节）。
- 用户原话本身的需求合理性（复述只需忠实，不评需求）。
