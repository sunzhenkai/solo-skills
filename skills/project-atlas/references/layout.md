# 系统视图与金字塔页面契约

## 两条阅读轴

系统视图回答“整体怎样协作”，领域金字塔回答“某块职责怎样实现”。两者通过链接汇合，不把跨领域流程强塞进某个领域。

| 层级 | 页面 | 应回答的问题 |
|---|---|---|
| L0 | `index.md` | 系统是什么、为什么存在、不同读者先读哪里 |
| L1 | `flows/<flow>.md` | 一条业务链路怎样跨领域从触发走到结果 |
| L1 | `architecture/<topic>.md` | 在线、离线、数据和模型组件怎样协作，故障怎样传播 |
| L1 | `data/<topic>.md` | 关键数据由谁拥有和写入，状态、事件与一致性怎样维持 |
| L1 | `cross-cutting/<topic>.md` | 某项全局机制影响哪些链路，策略在哪里生效 |
| L1 | `domains/<domain>/index.md` | 这个领域负责什么，边界与核心实体是什么 |
| L2 | `domains/<domain>/<topic>.md` | 一条领域内部逻辑怎样工作 |

系统视图按需建立。一个视图出现独立读者、复杂分支或多处引用时再拆页；每层可直接读，上级提供上下文，下级提供证据与细节。

## L0 总览

L0 至少包含：

- **系统边界**：服务的角色、外部参与者、价值与明确不在范围内的部分。
- **业务闭环**：从核心触发到业务结果，再到数据或模型反馈的闭环。
- **阅读路径**：按“理解业务”“排查线上问题”“修改某条规则”等读者目标链接到具体页面。
- **多视角导航**：直链所有 L1，并标出仍为 `draft` 的覆盖范围。

L0 只保留导航所需摘要，主链路的步骤、架构依赖和数据规则在对应视图展开。

## 系统视图内容

| 视图 | 必备内容 | 下钻链接 |
|---|---|---|
| 主链路 | 触发者、业务前提、有序步骤、每步责任领域、业务结果、关键失败与补偿 | 相关领域、架构、数据与横切页 |
| 架构 | 组件职责、同步/异步依赖、在线/离线/数据/模型边界、关键失败传播 | 主链路与组件所属领域 |
| 数据 | 核心实体与状态、读写方、事件、延迟、一致性边界、反馈去向 | 使用这些数据的主链路与领域 |
| 横切 | 策略目标、作用范围、执行点、对主链路的影响、降级或审计结果 | 受影响的主链路与领域 |

主链路页保留端到端顺序和跨领域关系，领域页保留内部规则的唯一解释。一个主题同时出现在多视角时，各页只写本视角所需结论并互相链接。

## 页面真源

每页使用以下 YAML 子集；`level` 写字符串形式的 `0`、`1`、`2` 也可，CLI 按文本比较：

```markdown
---
title: 订单处理
level: 2
status: draft
sources:
  - src/orders
  - src/payments/gateway.py
source_digest:
verified_commit:
---

# 订单处理

[返回领域](index.md)
```

- `title`：读者看到的主题名。
- `status`：`draft` 表示范围或内容尚未核全；`verify` 复核后写 `verified`。
- `sources`：源码根相对路径，支持文件、目录和 glob。L1/L2 进入 `verified` 前至少映射一个存在的路径。
- `source_digest`：由 CLI 根据映射文件的路径和内容计算；代码或未提交文件变化会改变它。
- `verified_commit`：复核时的 Git HEAD；非 Git 项目留空。

手写页面时后两项留空。使用 `verify --page <atlas-relative-page>` 更新复核信息，不手算摘要。

## 导航与链接

- L0 必须直链每个 L1；L1 必须直链所属 L2。
- 每个 L1 链回 `index.md`，每个 L2 链回本领域 `index.md`。
- 主链路直链涉及领域，相关领域链回使用该领域的主链路；架构、数据和横切页链接到它们解释的主链路。
- Archify 交互图使用 `diagrams/<slug>.html`，同名 `.json` 是可编辑图源；从相关页面用相对路径链接。
- 其他静态资源使用 `assets/` 内相对链接，例如 `assets/diagrams/order.svg` 对应的页面链接。
- Markdown 中保留 `.md` 扩展名；`build` 在 HTML 镜像中改为 `.html` 并保留锚点。
- 本地链接指向 Atlas 内已经存在的文件。源码追溯使用 `sources`，避免静态站点依赖仓库外路径。

## 内容粒度

架构页写组件职责、交互、边界和关键取舍；业务页写触发者、业务步骤、规则、异常和结果。函数逐行走读、完整文件清单、依赖版本和启动命令留在源码或项目既有文档中，只在它们解释架构契约时引用结论。

复杂分叉、状态机、跨系统时序和非平凡数据流配 Archify 交互图；线性三步用列表即可。图承担文字难以表达的结构，页面提供上下文与阅读重点，不把大图嵌进 L0。

## 复杂系统阅读验收

首批真实页面完成后，用一条核心主链路检查读者能否回答：

1. 谁参与系统，各自获得什么价值？
2. 核心请求怎样变成业务结果与后续反馈？
3. 每个关键决策由哪个领域、组件和数据决定？
4. 关键状态由谁写入，跨系统一致性怎样维持？
5. 某环节失败会怎样传播，补偿或降级在哪里发生？

尚未有证据支撑的问题对应页面保持 `draft`，在交付回执中列出，不用推测补齐。
