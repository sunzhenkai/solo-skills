# 降级必须以本次明确拒绝为前提，未表态时委派停住

- target: skills/agent-roster
- mode: update
- patch: 20260917-230721-degrade-requires-explicit-refusal
- risk: high
- status: proposed

## Intent

补住上一轮门禁（`20260917-220312-acpx-install-gate`）留下的缺口：`acpx` 不在 PATH 时，编排者仍然会直接走降级，且把上一次的降级当先例沿用。

改变三处行为：

1. `acpx` 缺失时**先停下委派**，提议安装并等使用者回答；等待期间不得改走降级。
2. 明确「使用者还没回答」这一中间态，并规定该状态下不得降级——沉默不等于拒绝。
3. 门禁按次生效：每次委派独立检查，上一次走过降级不构成本次豁免；本次的拒绝要记进 `decision.md`。

非目标：不实现新的降级客户端；不改探测脚本；不改权限两档的定义；不动仓库根 `README.md`（不在 skill 目录内，由使用者侧另行处理）。

## Conflict check

与上一轮门禁不冲突，是对同一条规则的收紧：默认选项仍是安装，仍禁止静默安装，仍要求拒绝后先提示受限。与「本 skill 不绑定具体执行器」不冲突——默认实现仍是 `acpx`，换执行器仍只改契约文件。与 L1/L2 探测不冲突：探测不经 `acpx`，门禁只在准备委派时触发。

## Rationale

上一轮门禁写了三态（已安装 / 未安装 / 使用者拒绝），唯一被禁止的动作是**静默安装**。「不装、直接降级」没有被任何一条禁止，于是编排者可以自洽地推出：不安装是合规的，那就走第 3 条。缺失的第四态（已提议、等回答）是每次询问都必然出现的状态，未定义状态下编排者会选当场能执行的那条路。

同时，第 3 条的前提「使用者拒绝」没有被限定为本次对话里真实发生的事件，也没有说明有效期，于是一次跑通过的降级会被当成既定做法沿用。真实失败即如此：门禁应用后的下一次委派仍然直接宣布「沿用既有降级路径」。

第三个成因是信息密度不对称：契约文件的降级段给出可直接照抄的协议步骤，门禁只有一句原则。把「进入条件」写到降级段开头，使照抄命令的人先撞上前提。

改动可验证：正文出现四态与「未获明确拒绝不得降级」，降级段以进入条件开头。
