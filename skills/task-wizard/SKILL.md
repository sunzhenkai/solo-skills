# Task Wizard：任务完成方案

产出**步骤级**、**可移交**的任务完成方案。不做详细设计——不画架构、不定接口、不写代码骨架；不执行——写完停下，交给下游（人、task-goal、task-explore 或 task-delivery）。

## 原则

- **先查后问**：能查到的（代码、文档、环境）先查，只有自己拿不准时才问；问前必给推荐答案。
- **步骤级颗粒度**：每步一个可执行动作，不超过 2 行，含「要点」与「验证方式」。
- **交付级但克制**：面向生产交付，不做成 demo。完成判据之外，把本任务应有的交付面写成可检查的「交付标准」，只取验证或测试覆盖、错误与边界行为、文档与配置等配套更新里与本任务相关的几条；不引入超出任务所需的架构、抽象或配置项，不相关维度不列。
- **阻塞点与坑必须显式列出**，没有就写「无」，不许省略小节。
- **简洁**：方案总篇幅控制在半屏内，是行动清单不是文档。

## 决策收敛

方案落稿前，把**所有要人拍板的缺口**收敛进方案：影响方案走向的歧义（在澄清意图时提问并带推荐答案）、未查证的假设、会卡住方案的阻塞点、执行中必须停下来要授权的动作——落稿时把它们分成两张清单写进「坑 / 注意事项」：①**需逐步授权**，即线上动作、泄密风险、破坏性 git、删除或不可逆改写、改密钥或权限、对外发送、不可逆迁移，这些始终要用户逐步点名，不在方案阶段执行；②**执行前授权清单**，即为走完本次步骤需要一次性放行的可逆、仓内、非线上动作。②所列动作，用户对方案的接受即视为已放行；未列进②的动作一律按①处理。方案交出后，下游只做「按此执行 / 调整哪步 / 改路由」三选一；方案里没列出的缺口，不允许在执行期冒出来向人要答案——执行中发现新缺口，由执行方自己的机制处理（goal 模式下走 task-goal 的审阅），不回流本 skill。

## 工作流

1. **澄清意图**：一句话复述目标与完成标准。歧义会影响方案走向时才提问（带推荐答案）；否则按最合理解释推进，并在「假设」中声明。
2. **摸底现状**：只读探查相关代码 / 文档 / 环境，把「已确认事实」与「假设」分开。
3. **数据备份检查点**：任务涉及数据写、删、迁移、改库表结构时，先判断备份方式与回滚路径，写进方案的「前提」或「步骤」。这里的回滚只针对**当前任务改动**——出问题时能快速回到本次改动前的状态，不要求全量历史回溯。大 size 数据难以备份、或本次改动不可回滚的，必须总结进「风险点」小节，不可省略。
4. **外部参照**：读并做完 [references/external-precedent.md](references/external-precedent.md)。必做范围：复杂档；中等档涉及选型 / 外部集成 / 协议对接。其余跳过。做完再写建议路由。
5. **产出方案**：按下方模板输出，并给出「复杂度路由」建议。
6. **对齐**：末尾问用户「按此执行 / 调整哪步 / 改路由」，不要默认直接开干。

## 输出模板

```markdown
# 任务方案：<任务名>

## 目标
<一句话说清完成标准>

## 交付标准
- <本任务应有的交付面要求；无则写「无」>

## 前提
- 事实：<已查证的现状>
- 假设：<未查证，方案基于此>

## 步骤
1. <动作> — 要点：…；验证：…
2. <动作> — 要点：…；验证：…

## 阻塞点
- <会卡住整个方案的事，以及需要先解决什么；无则写「无」>

## 坑 / 注意事项
- <易踩的坑、隐性依赖、顺序敏感点；执行中须停下来要授权的动作也写在这里；无则写「无」>

## 风险点
- <大 size 数据难以备份、本次改动不可回滚（无法快速回到改动前状态）等高风险项；任务涉及数据写删改时必须先评估备份与回滚路径，评估不通过或代价过高的在此显式列出；无则写「无」>

## 不做的事
- <明确排除项，防止范围蔓延>

## 建议路由
<简单 / 中等 / 复杂 之一 + 一句话理由>
```

## 复杂度路由

档位只取简单、中等、复杂，也就是复杂度的低、中、高。审阅侧的把握定级不参与选档。任务方案写进「建议路由」。先看复杂：命中任一条就是复杂。

| 复杂度 | 典型情况 | 衔接 |
|--------|----------|------|
| 简单 | 局部修改 | 本方案即 plan，先走 grill-with-docs 拷问方案、梳理清楚，再按步骤直接实现，不再产其他工件 |
| 中等 | 一个中等需求。可以跨多个模块或仓库，改动量稍大，或逻辑稍微复杂 | 先走 grill-with-docs 拷问梳理，再走 OpenSpec：委托 `openspec-propose`，经 `openspec-apply-change` 实施 |
| 复杂 | 项目级重构或逻辑重塑。业务逻辑复杂、涉及面广，也是复杂 | 走 task-explore → taskflow：先 task-explore，把本方案正文登记进 `TASK.md` 的「方案」小节（步骤 / 阻塞点 / 坑），再经 `explore`/`design`/`decide` 梳理清楚后 `handoff`，由 taskflow 建 `{task}-driver` 并委托 stock `openspec-*` 实施 |

- 命中复杂档任一条即复杂。单仓、顺序执行、没有并行，都不是降档理由。
- 产品交付硬指标，命中任一条即复杂，不得降档绕过质量门：多个主页面；两个以上生效角色或权限边界；持久化数据在多个请求或多个用户之间复用；外部系统集成、实时协作、通知、审计等跨模块行为；项目级重构、逻辑重塑，或业务逻辑复杂且涉及面广。仅改一个组件、单页原型、无持久化的静态演示不触发本条，仍按原档位路由。
- 跨多个模块或仓库本身是中等。同时属于项目级重构、逻辑重塑，或业务逻辑复杂且涉及面广时，升为复杂。涉及面广指多个业务行为或大块产品面都要改，不是只多碰到一个模块。
- 拿不准只发生在简单与中等之间，且没有复杂档典型情况时：往简单靠一档，并说明理由。已经命中复杂档时不得降为中等或简单。

- 路由是**衔接不是执行**：task-wizard 只把方案与结论交给对应流程，不代替它们做提案或编排。
- **先拷问后实现**：简单 / 中等两档实现前一律走 grill-with-docs，把方案里没想清的分支拷问掉再动手，不跳步。
- 委托 `grill-with-docs` / `openspec-*` / task-explore / taskflow 前确认当前环境能读到对应 skill；不可用时停下报告并给出安装选项（如 `dotf agents -c`），不自行发明等价命令。
- 路由到 grill-with-docs 时，逐字保留其两跳调用（`grilling` + `domain-modeling`），不简写、不替换。
- 路由到 task-explore 时，**逐字带上方案正文**（目标 / 事实 / 假设 / 步骤 / 阻塞点 / 坑 / 不做的事），并点名落点：`new` 时登记进 `TASK.md` 的「方案」小节；只作输入，不下新任务名、不重复已查证的摸底。
- 复杂档的正文在交出前已含外部参照：对上出处的在事实里，对不上的在假设里。上述原文原样带给 task-explore。
- 路由到 OpenSpec / taskflow 时，把方案正文（目标、步骤、阻塞点、坑）作为任务描述原文带入，不让下游重新猜意图。
- 方案由处在 goal 里的执行方接收时（如 task-goal、task-delivery 的 goal 模式），方案原文同样是唯一载荷；执行中的确认与审阅走 task-goal，本 skill 不参与。

## 边界

- 任务方案里涉及线上环境（生产、预发、共享远程）的步骤，标注「需逐步授权」，不在方案阶段执行。
- 发现任务实际是「写详细设计 / 直接改代码 / 排查 bug」时，说明并退出本流程，不硬套模板。
