# Agent API 操作规范（agent-api-ops）

> 本文件是 project-design-patterns「agent 数据接入」模式的**操作规范件**，随该 skill 一起发布与安装；原独立 skill `agent-api-ops`。各应用设置页的接入话术安装 `project-design-patterns` 后，按本规范操作。

面向用户的输出默认使用简体中文。命令名、路径、代码、状态值与既成术语保持原文。

把应用设置页发给你的「接入话术」变成可长期使用的 API 操作能力：凭证落盘成稳定配置，之后每次操作应用数据都走 HTTP API。应用的全部业务功能（增删改查、推送、配置）都经 API 完成；凭证管理（创建/删除 Key、登录登出）属于应用端能力，按话术与应用 UI 的说明交还用户处理。

## 接入流程

1. **解析话术**：必含两项——API Base（服务地址）与 API Key（形如 `hela_sk_…`、`sk_willow_…` 等应用自定义前缀）；可能附带安装指引、skill 接口地址或端点概览。缺少任一项时向用户索取完整话术。
2. **按话术安装**：话术要求安装某个 skill 时先执行其安装命令（如 `npx skills add <owner>/<repo> -s <skill> -g -y`），安装内容以装到的 SKILL.md 为准；本规范随 `project-design-patterns` 安装，与具体应用的专属 skill 并行使用。
3. **保存凭证**：按下节约定落盘并回执「已保存 + 保存位置」，首次接入后做一次探活。
4. **后续使用**：用户再提「操作 <应用>」时，先读已保存的配置再调用；配置缺失时向用户要新话术，而非猜测地址。

## 版本与更新（响应头懒触发）

- 操作规范版本 = 本 skill（`project-design-patterns`）`SKILL.md` frontmatter 的 `version`；应用服务端可在响应头返回 `X-Patterns-Version` / `X-Skill-Version`，并在 `{base}/skill.md` 头部以 `skill: project-design-patterns@X.Y.Z` 声明所依据版本。
- **平时直接干活，按触发条件懒刷新**（避免每次会话空跑探活与 `/skill.md` 拉取）：
  1. 首次新接入（尚无本地凭证或本地端点快照）时，拉取一次 `{base}/skill.md`（若免鉴权可直接拉）并验证一个只读端点；
  2. 已有本地凭证与端点快照时，直接发起业务请求；
  3. 仅当业务响应头 `X-Patterns-Version` 高于本机 `project-design-patterns` 版本、或收到 `404` / 契约不匹配时，再拉取 `{base}/skill.md` 并按需升级（`npx skills add sunzhenkai/solo-skills -s project-design-patterns -g -y`，尽量交给 subagent 执行）；
  4. 应用未声明版本或无 `/skill.md` 时直接按现版本操作。

## 凭证保存与读取约定

- 统一读取顺序（命中第一个非空，避免多机/多脚本分裂）：**当前环境变量** → **`~/.agent-state/app-keys/<app>.env`** → **`senv env get svc:<APP>_API_BASE` / `svc:<APP>_API_KEY`**（如环境已接 senv）。
- 本地落盘位置：`~/.agent-state/app-keys/<app>.env`，`<app>` 取话术中的应用名小写（如 `hela`、`llmwiki`）。
- 内容两行：`APP_API_BASE=<base>`、`APP_API_KEY=<key>`；文件权限 `600`，目录不存在则先创建。
- 该文件属于个人凭据：保存后向用户确认；输出与日志中只显示 key 前缀（如 `hela_sk_abcd…`），完整明文只在用户明确要求时出现在本地配置中。
- key 泄露或换设备时提醒用户：在应用设置里删除旧 Key 重建，并更新本文件或 senv。

## 认证与调用

- 所有请求带 Header：`Authorization: Bearer <APP_API_KEY>`；认证信息只放 Header，与任何查询参数、日志无关。
- 首次接入探活：优先调应用的 health/me 类端点；无此类端点时，按「API 详情获取策略」拿到文档后用第一个只读端点验证 200。
- 4xx 语义与动作：
  - `401`：Key 无效或已被删除，停止重试，提醒用户到应用设置重建并更新保存的配置。
  - `403`：该操作应用侧保留给会话/管理端（如凭证管理），向用户说明并停在应用端完成。
  - `404`：核对端点路径与 base URL；必要时按「API 详情获取策略」刷新文档。
  - `429` / `5xx`：指数退避重试至多 2 次，仍失败则报告错误原文。
- 响应体为 JSON 时按字段原样转述给用户（ID、时间、数量等关键字段保留原文）。

## API 详情获取策略

按优先级取操作依据，高优先级存在时以其为准：

1. **应用的 skill 接口**：话术或应用文档提供 skill 文档 URL（常见形如 `GET /skill.md`）时先拉取，内容随部署版本发布，是该版本 API 的权威说明。
2. **话术内嵌端点概览**：应用没有 skill 接口时的兜底，以话术直接给出的端点表为准。
3. **应用文档**：话术指向的 README / API 文档链接。

端点在三类来源都未覆盖时，向用户确认后再尝试，不凭空构造路径。

## 操作纪律

- 先读后写：写操作前先 GET 同类资源确认字段形状与现有值。
- 删除、覆盖、批量修改类操作先向用户复述目标并等确认；创建类操作做完即报结果。
- 每次操作向用户报告：做了什么、命中哪个端点、结果关键字段。
- 操作记录只在对话中呈现；应用数据的沉淀交给对应的知识/笔记工具，本规范保存的仅是凭证与接入信息。
