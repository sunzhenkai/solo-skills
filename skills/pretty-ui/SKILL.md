# Pretty UI

做出一眼看得出被设计过的界面。三条信条贯穿所有模式：

- **地板靠规则**：层级、间距、排版、色彩、对比、状态按 [rules.md](references/rules.md) 扫查，每个问题都指得到规则号。
- **天花板靠方向**：从品类、受众和内容推出一句北极星和一张方向卡，力气花在一个记忆点上，其余安静。
- **以画面为准**：看过真实截图才算看过；读源码只能证明实现与设计一致，证明不了好看。

## 路由

| 请求 | 模式 | 做法 |
| --- | --- | --- |
| 点名的小改：改色、调间距、改文案、删指定元素 | 小改 | 直接改；动了颜色、间距或样式，就在目标视口看一眼改动处和相邻元素 |
| 新界面、整体改版、单组件打磨、照参考图还原 | build | 走下方主流程；照图还原时参考图就是方向，同视口截图并排比到位 |
| 已有界面不好看、要优化 | refine | 先截图诊断出带规则号的问题，按扫查顺序修，沿用既有体系，交付前后对比 |
| 只要评审 | review | 只读，不改文件；按 [critique.md](references/critique.md) 出问题清单 |
| 配色、设计规范、项目还没有设计系统 | system | 按 [system.md](references/system.md) 生成刻度、校验对比度，产出 `tokens.css`、`DESIGN.md`、`preview.html` |
| 把文件、报告、方案做成浏览器阅读页 | page | 按 [page.md](references/page.md) 落盘，视觉走 build 的轻量版 |

意图混合时按顺序串起来并说明，例如在没有设计系统的项目里做设置页，就是 system 再 build。多角色、按岗位的评审走 role-based-reviewer。

## build 主流程

1. **探测**：技术栈、已有 token / 组件库 / 品牌规范、暗色模式、交付物形态（设计说明、原型、可运行界面）。
2. **简报**：用户、主任务、真实内容、设备；把内容排成主 / 次 / 辅，动作排成一个主操作、几个次要、若干辅助。写进设计说明或文件头注释，让评审能核对。
3. **方向**（未定才做）：按 [direction.md](references/direction.md) 认品类、拆标杆、定调性、写方向卡并做差异检验。独立使用且方向未定时，写三个文字方向加推荐，问用户一次，本轮结束；用户说“你定”、上游是 goal 模式或无人值守时，自选并写明理由。用户给了品牌、参考图或说清了风格，方向即定，只补方向卡缺的栏。
4. **体系**：按 system.md 取值；新色阶用 `scripts/palette.py` 生成，文字与背景的配对用 `scripts/contrast.py` 校验。
5. **构建**：先做一页代表页或一条关键流程。顺序：灰度下立层级 → 间距与分组 → 行长与节奏 → 上色 → 深度 → 收尾。空、加载、出错状态和像真的数据随功能一起做。
6. **看图**：桌面 1280 与手机 375 各截一张，关键区域按 100% 看；修掉重叠、裁切、溢出和孤字。
7. **批评**：按 critique.md 自查扫查、做减法；新界面和整体改版派隔离评审。按“重做 → P0 → P1 → 提升”的顺序改，“保留”的做法不磨平；两轮后仍有 P0 就停下说明。

## 十条铁律

每个任务都适用：

1. **每屏一个主角**：强调靠压低旁边的元素，而不是继续给主角加码。
2. **先灰度后上色**：字号、字重、明度和留白在灰度下就读得出主次；颜色只做强调和语义状态，强调色有用量预算。
3. **取值来自刻度**：字号、间距、色阶、圆角、阴影、边框都从体系取；缺就先补 token。
4. **组外距离大于组内**：标题贴近它下面的内容，标签贴近自己的控件。
5. **正文限宽**：中文每行约 30–40 字（上限 46），英文 45–75 字符；宽表格、代码、图解在自己的容器里用满宽或横向滚动。
6. **可读是门槛**：中文阅读页正文 16–18px、行高 1.6–1.75，产品界面正文 14–16px，密集工具 13–14px；正文对比度至少 4.5:1，大字至少 3:1。
7. **有色底上用同色相降对比**，而不是灰字或半透明白；含义同时由文字或图标承载，颜色只是加强。
8. **结构即信息**：编号、眉标、分隔线、卡片、标签只编码真实的顺序、层级或语义；一处分隔只用一种手段，容器只套一层。
9. **内容像真的**：真实长度、不整齐的数据、说清动作的按钮文字；只呈现输入里真实存在的事实。
10. **既有体系优先**：沿用项目的 token、组件、品牌色和字体，缺口按它的命名补；规则与项目的刻意约定冲突时指出冲突，约定先行。

## 看图与证据

- 截图工具按序选：宿主的浏览器工具 → 项目已有的截图或 e2e 工具 → taskrail 的 `scripts/ui_evidence_check.py`（需要 playwright）。都用不了时，结论标“未渲染验证”，问题标 `code-only`，交付里如实写没看过画面。
- 生成的静态页面先跑 `python3 scripts/check_page.py <路径>`（脚本路径相对本 skill 目录）：报错项修好再交，提示项逐条改掉或在交付说明里写理由。
- 截图、设计说明和评审记录放任务目录或项目约定位置，本 skill 目录保持只读。

## 交付

交付说明逐项写到：选定的方向与理由（沿用既有体系时写沿用了什么）；改了什么、哪些没做及原因；截图与证据路径；评审方式、轮次与结论（自查还是隔离评审）；减法删了什么；未验证项。
