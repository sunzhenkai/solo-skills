# UI 工程化（token 与组件）

[pretty-ui](../SKILL.md) 的 system 工程化分支读本页：项目初建时补齐 UI 体系，已有项目架构优化时收敛 token 与组件。目标减少同职责实现与样式取值漂移，不让所有页面失去刻意差异。

## 1. 分支与边界

- `init`：项目已有空壳、技术栈或目录约定，设计体系尚未完整。沿用现有栈、组件库和命名，补齐语义 token、当前需要的组件契约与证据页。
- `audit`：已有实质 UI 源码，要求工程化检查或架构优化。只读产品代码、依赖与配置，报告直接给出；用户要求落盘时写 `UI_AUDIT.md`。用户明确要求统一、迁移或实施后才改实现。
- 脚手架、框架选择与依赖初始化走 `project-init`；本分支不改技术栈、品牌与视觉方向，不新增依赖，优先使用项目已有组件和工具。

开始先读 manifest、现有 `DESIGN.md`、token / 主题文件、组件目录、Storybook / preview 与代表页面。完成：分支、范围、沿用项与目标产物写清。

## 2. 盘点

按项目结构定向搜索，记录文件与行号、使用次数和代表调用方：

- token：CSS 变量、Tailwind / 主题配置、色阶、字阶、间距、圆角、阴影、暗色映射。
- 组件：共享组件、页面私有组件、组件库封装、直接写样式的页面区域。
- 证据：组件故事、preview、页面测试、视觉回归和现有例外说明。

同职责组件列出 API、variant、状态与页面采用情况；同职责样式列出实际取值和来源。完成：每项决定都能指到实现与调用方，不只凭文件名判断重复。

## 3. Token 检查

- 颜色、字号、间距、圆角、阴影有散落字面值时，判断它属于基础刻度、语义用途还是一次性例外。
- 名称不同但职责相同的近似值合并；缺语义用途时补语义层，不再造一条相近色阶。
- 组件消费语义 token，不直接引用基础色相或临时调亮、调暗；语义色只表达对应状态。
- 暗色模式重新映射语义层；真实文字 / 背景配对按 system.md 校验对比度。
- 有产品依据的例外保留并记录位置与理由，不把字面值数量机械压到零。

token 的刻度、命名与生成规则按 [system.md](system.md)，本页不另建一套。

## 4. 组件检查

- 同职责多份实现：确定保留、合并、扩展或退役，页面绕过共享实现时一并列出。
- API 分叉：统一同义的 variant、size 与状态命名；不同职责不为了复用而塞进一个组件。
- 状态缺口：检查默认、悬停、聚焦、选中、禁用、加载、空、出错中该组件真实需要的状态。
- 一致性：样式只消费语义 token；图标、焦点、点击区域和键盘行为沿用同一约定。
- 抽象边界：只出现一次、职责独立的结构留在页面，不因为局部样式相似就新建共享组件。

每个保留或新增的共享组件在 `DESIGN.md`、组件文档或项目既有位置写清契约：

| 字段 | 内容 |
| --- | --- |
| 职责 | 解决什么 UI 任务，不承担什么 |
| API / 变体 | props、variant、size 与命名来源 |
| token | 消费的语义 token |
| 状态 | 必须覆盖的交互与数据状态 |
| 可达性 | 键盘、焦点、名称与点击区域 |
| 示例 | 一个真实调用方或故事 |

## 5. 决定与审计输出

每个问题选一种决定：**保留 / 合并 / 扩展 / 退役**。刻意差异和一次性结构选保留并写理由；只有调用方证据支持时才合并或抽象。

`audit` 报告及要求落盘的 `UI_AUDIT.md` 包含：

| 字段 | 内容 |
| --- | --- |
| 编号与严重度 | P0：可用性、可达性或关键状态；P1：体系分叉与共享实现绕过；P2：文档、示例与轻微命名 |
| 证据 | 文件与行号、使用次数、代表调用方 |
| 现状与目标 | 当前实现、目标 token / 组件契约 |
| 决定 | 保留、合并、扩展、退役及理由 |
| 批次与风险 | 代表页或后续批次、影响页面、回归风险 |
| 验证 | 项目原生检查、组件证据与页面截图 |

报告同时列无问题的已覆盖范围、刻意保留的例外和未检查项。完成：每个 P0 / P1 都有证据、目标与验证方式，不用“建议统一”代替迁移决定。

## 6. 实施顺序

用户明确要求实施后，按以下顺序小批修改：

1. **语义 token**：先建立映射，保留项目命名与刻意例外。
2. **基础组件**：只改本次范围内重复或缺契约的共享组件。
3. **代表页面**：先迁移一个覆盖主要变体与状态的页面，跑通验证。
4. **批量迁移**：按使用次数与回归风险分批替换调用方。
5. **清理旧实现**：调用方迁完后删除或退役旧路径，避免新旧两套长期并存。

每批保持对外行为与公开 API 稳定；确需 breaking change 时先写明影响和迁移方式。完成：代表页通过后再扩大范围，每批都有可回退的独立改动。

## 7. 验证与完成门

优先运行项目已有的 typecheck、lint、test、build 与视觉回归；没有对应工具时在交付里写未覆盖项。再按产物补：

- 真实颜色配对跑 `scripts/contrast.py`；静态 preview 跑 `scripts/check_page.py`。
- Storybook 或 preview 覆盖本次组件的变体与状态；代表页面按 [evidence.md](evidence.md) 留改前改后证据。
- 调用方搜索确认目标旧实现已无引用，保留例外仍能指到理由。

`init` 完成：token、当前所需组件契约和证据页可使用，项目原生冒烟通过。实施完成：范围内 P0 / P1 已修或明确列为范围外，验证通过，旧实现按批次清理。`audit` 完成只要求报告达到第 5 节，不以修改产品代码为完成条件。
