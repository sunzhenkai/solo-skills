# 批评与评审

[pretty-ui](../SKILL.md) 的自查、隔离评审、review 模式与迭代停止读本页。规则号见 [rules.md](rules.md)，截图与量测见 [evidence.md](evidence.md)。

## 1. 自查

会派隔离评审时（新界面、整体改版、goal 模式的观感验收），制作者只做下面第 2–4 条，完整扫查和问题表交给评审者；不派评审时四条都做。

1. 先过 rules.md 的 X 组，再按 H → S → T → C → D → I → F → M 扫，每条问题填进「问题表」。
2. **做减法**：逐屏看哪些文字、面板、数据、装饰可以删或合并；填缝短句、界面上的设计说明、“示例”“仅供示意”照删。每加一个新元素，写明为它腾位置删掉了什么。删完主角更突出才算删对。
3. **眯眼看**：只看明暗块面，确认主角就是第一眼看到的东西。
4. 处理 `scripts/check_page.py` 的提示和 evidence.md 的量测结果，逐条改掉或写理由。

## 2. 隔离评审

制作者很难看出自己的默认做法。新界面、整体改版、goal 模式的观感验收、用户要求评审时，派一个没参与制作的评审者：另一个模型或子代理（在 taskrail 任务里按其 `confirm-protocol.md`「另一个模型审」派）。

- **交给评审者**：截图与量测结果的路径；任务和用户是谁；约束（品牌、字体、主色、不能动的组件和导航）；北极星、方向卡与参照（取它哪一点，含方向第 1 步存下的标杆首屏）；`check_page.py` 的提示；本节的评审手册。
- **留在手里**：源代码、制作者对自己选择的辩护、上一轮的结论。第二轮起只把上一轮的问题清单和复审档截图交过去，让评审者逐条核对是否修好。
- 评审者只评审，不改文件，不再派别的评审者。

## 3. 评审手册

拉高标准，以“这个品类里最好的团队会怎么做”为标尺。分清看得见的缺陷和个人偏好，没有明显问题就直说，不为凑数提意见。没看到、没法验证的写明；只有静态截图时，写“没看到动效”，不对操作流程下结论。

0. **三秒测试**（先于一切细节）：看 480 宽缩略图（evidence.md 第 2 节）三秒，再看把文字遮掉的版本三秒，写两句话：它像哪一年的哪一类产品；第一眼看到的是什么。像几年前的通用产品、组件库默认样子或素材库配图，直接写出来。说服型页面的主视觉换到别的产品上同样成立，说明辨识度不够；工具、后台沿用侧栏、工具条、表格等高效基线不算问题，看的是表面是否干净透气、核心关系和异常是否一眼可辨。
1. **品类与标杆**：一句话说出品类，以及标杆在首屏怎么做；指出偏离共识的地方，判断是有意创新还是套了默认模板。
2. **规则扫查**：X 组，再 H → M，每条问题带规则号。
3. **动效**：主操作有没有反馈，状态切换看不看得出来路，首次进入有没有出场；说服型页面再看各区块是否按自己的内容出场。确实没做的写进问题，做得好不好放进提升。
4. **提升**：缺陷清零常常只是及格。精致度、设计感、动效三项逐项表态，有看得见的差距才写，没有就写“没有”和依据。提升是把已有的东西做得更好，不是再加东西。
   - **精致度**：200% 下哪个组件最粗糙（字距行距、图标与文字对齐、阴影描边、各状态一致性）；100% 下的中文断行、孤字、数字格式；整页标题和正文块的左边缘起点是否收在两三条锚线上。
   - **设计感**：主角在缩略图里看不看得见；哪一处最接近品类最好水平、还差什么；哪一处仍是组件库默认样子。给每一屏的构图起一个词（分栏、大字列表、满版图……），同一个词连续出现两次或全页出现三次，就是模板复读。检查节奏与收尾：是否每一屏都塞进带底色或边框的盒子，首屏有风格、下面却退回通栏细线加默认输入框。
   - **动效**：哪一处动得机械（匀速、各动各的、全页一律淡入上移、和操作接不上），哪一处最值得做出手感；手感用“动作 + 实物参照”写。
5. **精简**：点名可以删的文字、面板、数据和装饰；删完主角没有变强、画面只是变空，或具体信息被套话替代，同样算问题。

### 结论与输出

- **结论三选一**：
  - **重做**：首屏骨架仍是模型默认模板，或主视觉远低于同品类水准。第一条写“重做：”，点名要重做的区块和原因，这些区块不再列修补建议；在被否定的骨架上修补，只会把它修得更像样。
  - **需改**：有 P0，或有影响观感的 P1。
  - **通过**：没有 P0，剩下的 P1、P2 不影响主任务和观感，可以随交付说明列出。
- **顺序**：开头一份速查清单，每行一条 `[P0-1 / 提升 1] 位置：现象 → 修完要达到的可验收结果`，方便逐条勾销；再给「问题表」；然后是提升。P0 全部列出，其余问题按影响排序取最重要的几条（问题与提升各不超过五条），更小的合成一句放最后。
- **改法写目标**：写修完要达到什么，不替制作方定构图，不规定放多少对象和数据，不靠加功能、加数据换真实感；要求新增元素时，同一条里写明为它腾位置删掉什么。
- **倒数第二行**写“保留：”，点名一两处修改时不能磨掉的做法，通常是这个方向最有辨识度的地方。
- **最后一行**写结论（重做 / 需改 / 通过）。不打数字分：不同模型的分数没法比较，三态结论加问题清单才能直接指导下一步。

## 4. 存量界面对齐评审

用户要在现有产品里润色、而不是换风格时用这一节：标尺是产品自己的规范，而不是评审者理想中的风格，不给“重做”结论。

- **规范来源**：成文规范，或从现有设计变量、共享组件和同类页面整理出的现状规范，加上不能动的品牌、字体、主色、组件库和导航。现状不一致时以多数做法为准，少数做法记为待统一；规范本身有问题的单独列出，交给用户决定。
- **检查**：哪里用了规范以外的颜色、字号、圆角，哪里明明有现成组件却手写了一个；在规范范围内最影响完成度的三处（层级、对齐、留白、减法）；这次改动涉及的动效有没有到位、有没有把原来的改坏。
- **输出**：客观的修正建议和可删的文字；不建议更换品牌色或字体。

- **镜头**：层级、间距布局、排版、色彩、深度、图像图标、收尾状态、动效、AI 默认样貌。
- **位置**：截图里的区域名，或 `文件:行号`。
- **验证**：在截图里看到的写 `rendered`，只从源码推断的写 `code-only`。
- 排序：P0 在前，同级按扫查顺序。

## 6. 迭代与停止

本节是 pretty-ui 怎么改、何时停的唯一标准，SKILL.md 与上游流程都指向这里。

- 按“重做 → P0 → P1 → 提升”的顺序改，“保留”的做法不动。
- 每轮改完按 evidence.md 的复审档重截，评审者拿上一轮清单逐条核对；交付前的最后一轮补状态档。
- 复审核对上一轮问题和本轮新引入的 P0；新发现的 P2 与提升写进交付说明，不因此再开一轮或补状态截图。
- **收敛**：结论是“通过”，即不是重做、没有 P0、没有影响观感的 P1。goal 模式自己迭代到收敛；剩下的 P1、P2 与提升写进交付说明。
- **停**：同一个问题连续两轮没改好，停下说明卡在哪、试过什么、需要什么（在 taskrail 任务里按其「卡住」规则停）。
