# Session Wrap

收尾目标：**让已完成的事彻底放手、不再挂念任何遗漏；主线未完成时，先确认继续做完还是中止**。

默认两轮：**第一轮只读自查亮清单等确认；第二轮按确认范围执行并给明确放手结论**。只要涉及写文件、改 git、停服务、删资源或外部操作，一律先确认再动手；已完成且完全无事可做时，直接告知可以彻底放手。

`anti-lazy` 负责交付前查意图差距；`taskrail` 的 `close` 负责任务 SUMMARY、状态和归档。本 skill 面向会话兜底收尾，复用它们的产物，不重复造轮子。

## 1. 先判完成度，再查闭环与现场（只读）

只查本次相关的真实现场，区分事实、推测和未知；纯问答或方案讨论只依据对话收尾，不扫描仓库。

- **完成度裁决（第 0 步）**：重读最初目标和最新要求，让每项明确要求对应到产物、回答或证据，区分已验证、未验证、未解决；原始场景和每项「必须」都要有结论，核心验收缺口留在本次处理，编译或静态检查不能替代原始场景验证。
  - **未完成**（任一明确要求未达成、原始场景未过或存在阻塞，或用户半途喊停）→ 按 [references/incomplete-abort.md](references/incomplete-abort.md) 列现状差距并请用户三选一（继续做完 / 暂停挂起 / 彻底放弃），跳过合入主分支、打 tag、发版或部署等完成态检查。
  - **已完成** → 按序核对以下三项：
- **交付闭环**：
  - **代码交付闭环**（多仓/多 worktree 逐仓核对）：
    1. 有未提交改动或未跟踪文件 → 安排提交（走 `commit-push`）。
    2. 在非默认分支（或本地默认分支领先远端）且有未推送或未合入主分支的提交 → 已有 MR/PR 核对 CI 与评审；尚无则按 [references/branch-merge.md](references/branch-merge.md) 推荐「推送并提 MR/PR」或合入主分支。
    3. 命中发布或部署信号 → 有版本 tag 惯例、发布/部署流水线或改动涉及服务/制品/版本时，按 [references/release-deploy.md](references/release-deploy.md) 只读核对版本、目标环境与合入前提并纳入拍板（未命中跳过）。
    4. 已合入或已提 MR/PR → 再评估清理 worktree 和临时分支（清理前先核对无未提交改动、无独有未推提交，未知文件保留）。
  - **非代码交付**：文档、配置、脚本、调研或外部回复，核对产物已放至目标位置或发出，无半成品草稿。
- **现场清空与任务状态**：核对临时服务、后台任务、容器/端口、临时文件与 `git stash`，以及调试日志、mock、跳过校验开关或临时配置是否还原；`taskrail` 任务完成态交 `taskrail` `close`（`done` 并归档），暂停/放弃态按 [references/incomplete-abort.md](references/incomplete-abort.md) 处理。
- **遗留落宿与按信号附带沉淀**：无关但有证据的旧 bug、技术债、过时文档或环境隐患归为遗留，须给出持久落点或确认不跟踪（见 [references/plan-synthesis.md](references/plan-synthesis.md)）。跨任务有复用价值的内容按同表路由；排查绕过明显弯路时按 [references/detour-review.md](references/detour-review.md) 做弯路复盘，产出坑候选（仅命中信号时附带）。

## 2. 汇总简明清单，等用户确认

- **未完成路径**：先说清已做到哪、还差什么，抛出「继续做完 / 暂停挂起 / 彻底放弃」三选一；选「继续做完」则退出收尾回到主线；选「暂停挂起」或「彻底放弃」按确认清单执行。
- **完成态路径**：合成短清单，每个发现只出现一次，按依赖排序：**补验当前缺口 → 提交 → 推送与提 MR/PR 或合入主分支 → 打 tag / 发布 / 部署（命中项目信号时） → 任务收口与现场清空 → 遗留落宿 → 按信号附带复盘与沉淀 → 衍生处理**。

按风险分成三块（细则见 [references/plan-synthesis.md](references/plan-synthesis.md)）：

- **需要你拍板**：有两种以上合理做法，或涉及未完成方向选择、git 写入、远端/共享分支、提 MR/PR、合入主分支、打 tag / 发版、部署、丢改动/关草稿 MR/删 worktree、写外部 tracker、无持久台账时遗留去向或放弃确认。每项一题，2–3 个选项，推荐项放首位并附一句理由；外部或不可逆动作一项一题，写明目标分支、版本或环境。
- **准备帮你做**：本机、可逆、结论唯一的低风险动作（记入已有台账、停本地服务/容器、还原调试开关、归位临时文件、更新暂停断点、落点唯一的坑候选写 wiki）。打包列出来，确认后一起执行。
- **顺手记下的遗留（这次不做）**：超出本次目标的缺口，写明去向；用户点名才另开任务。

## 3. 确认与执行

- **先确认后动手**：第一轮只做只读排查与列清单，写文件、改 git、停服务、删资源或外部调用一律等确认后再执行。即使清单里只有「准备帮你做」而没有选择题，也先亮出来等用户点头；只有完全无事可做时才直接结束。
- **授权隔离**：每项选择只授权该项，提交不等于授权 push，push 不等于授权合入主分支，合入不等于授权打 tag / 发版或部署，打 tag / 发版不等于授权部署，测试环境部署不等于授权生产部署；暂停挂起不授权合入或删分支/worktree，放弃撤场涉及的丢弃改动、关 MR/PR 或删分支须逐项确认。执行中新发现加项或风险升级时，停下来再问一轮。
- **路由执行**：提交/推送走 `commit-push`，提 MR/PR 或打 release tag 走 `repo-manager` 或 `gh` / `glab`（详见 [references/branch-merge.md](references/branch-merge.md)、[references/release-deploy.md](references/release-deploy.md)），发版与部署按项目脚本、CI 或对应 skill 执行，任务收口走 `taskrail` `close`（完成 `done`，放弃 `archived`；暂停保持 `active` 并更新断点），知识沉淀走 `wiki-data` 或 `skill-upgrader`。

## 4. 面向用户的输出（说人话、短、给放手结论）

- **说人话**：用白话短句说清“差什么、建议怎么做”，把内部词（`criterion`、`落点`、`建议处置`、`恢复入口`、`合入通道`、`按选择跳过` 等）留在后台。
- **控长度**：每条一行短句，空区块省略；路径和命令只在方便核对或恢复时顺带附上。第一轮尽量控制在半屏以内。
- **不重复**：宿主有结构化提问工具时，「需要你拍板」直接放进提问工具，正文只留现状摘要与其余区块，两边不重复列选项。
- **明确放手结论**：第一轮不下结束结论；第二轮开头用一句大白话交代现状并点明四种终态之一，再列做了什么、什么没做、遗留或断点在哪：
  1. **彻底收工**：明确可以彻底放手、不用再管；
  2. **本地收尾、剩外部等待**：点清唯一还需回看的外部异步项（MR 链接、等 CI/评审、是否开自动合并），其余全清；
  3. **已暂停挂起**：写明改动/分支/worktree 在哪、停了哪些服务、下次从哪接手；
  4. **已确认中止**：写明丢弃/关闭了哪些半成品、任务已按未完成归档、保留的有效经验（如有）。
  已完成且完全无遗留时只回一句可以彻底放手，不生成额外报告文件。

正反示例见 [references/plan-synthesis.md](references/plan-synthesis.md)。退出事件需宿主 hook，不能由 skill 自身保证捕获。
