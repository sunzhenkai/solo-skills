# 发布与部署检查细则（按项目信号触发）

本次会话有代码、配置或产物改动时，先只读检查是否命中发布或部署信号；命中至少一项信号时，必须把「打 tag / 发布 / 部署」纳入收尾检查，未命中则跳过，不向无发布机制的仓库多问无关问题。

## 1. 只读信号识别

- **会话与变更信号**：本次目标或对话提到发版、打 tag、升级、部署、上线；或改动直接影响可运行服务、构建产物、包版本（如版本号文件、容器镜像配置、部署清单、发布脚本）。
- **项目发布信号**：仓库存在版本 tag 历史（如 `git tag` 有 semver 或测试线/稳定线前缀惯例）、CI/CD 发布或部署流水线（如 release/deploy workflow 或 stage）、Makefile / package.json 的 release / publish / deploy 目标，或仓库 `README.md` / `AGENTS.md` 规定的发布部署流程。
- **环境与现状信号**：已接入制品库、包仓库或部署目标环境，或改动已合入/即将合入默认分支且领先最近 tag。
- **未命中则跳过**：纯问答或方案讨论、仓库无发布/部署/tag 机制、或改动仅为不影响产物的文档或本地草稿且对话未提发布部署。

## 2. 只读核对

给出推荐前，能查到的现场事实先查清，不拿去问用户：

- **合入与验证前提**：改动是否已提交、已推送、已合入默认分支及 CI/验证状态（仍在特性分支待合入时，说明与合入的先后关系）；
- **版本与 tag 现状**：最近一个 tag、相对最近 tag 的提交摘要、仓库既定的 tag 命名与版本递增规则；
- **渠道与目标环境**：具体发布渠道（Release、包仓库、制品库）和部署目标环境（测试 / 预发 / 生产），以及项目既有的发布脚本、CI 触发条件或宿主已装的对应发布/部署 skill；
- **生效验证与回滚指向**：发布/部署后如何验证生效、异常时如何回滚（如切回上一 tag 或版本）。

## 3. 推荐与逐项拍板

将命中项归入「需要你拍板」，给出 **1 个主推荐**（2–3 个选项，推荐项放首位并附一句白话理由）：

- **仍在特性分支未合入默认分支、且项目无预发布或测试线常规动作**：推荐「先等 MR/PR 合入过 CI，暂不打 tag/部署」（附后续入口）；若项目常规走测试线 tag 或预发验证，则标清前缀与环境供选择。
- **已合入默认分支（或本轮目标明确要上线）且命中信号**：推荐按项目既有流程推进，写明具体版本号或 tag 规则、发布渠道或目标环境。

拆分与授权隔离：

- 「打 tag / 发版」与「部署到具体环境」分题确认；多个环境（如测试、预发、生产）各自一题，题干写明版本、渠道或目标环境。
- 合入主分支不等于授权打 tag / 发版或部署，打 tag / 发版不等于授权部署，测试环境部署不等于授权生产部署。

## 4. 确认后落地与汇报

- **复用既有渠道**：优先复用项目既有发布/部署命令、CI 触发方式或宿主已装的对应 skill（如 `repo-manager` 打 release tag、或适配的发布/部署 skill），避免另起手工步骤。
- **执行前核对**：核对工作区干净、目标 commit 与 CI 状态，遵守目标环境与接收 skill 的确认门禁。
- **第二轮汇报**：写明实际 tag 名、Release/制品链接、目标环境、生效验证结果与回滚指向；若用户选择暂不发布或部署，如实写明「本次暂未打 tag / 未部署」及后续触发方式。
