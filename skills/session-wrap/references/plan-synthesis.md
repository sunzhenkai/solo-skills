# 收尾清单、分流与说人话示例

本文件规定收尾清单的归属判据、提问规则、缺口记账落点、知识沉淀分流与面向用户的输出示例。

## 1. 动作分级（确认后才执行）

所有会产生副作用的收尾动作都必须在第一轮亮出、等用户确认后再执行：

| 区块 | 适用范围 | 典型事项 |
| --- | --- | --- |
| 需要你拍板 | 有两种以上合理做法，或涉及 git 写入、远端、不可逆、跨机或外部系统 | 补验方式、提交范围、push、提 MR/PR、合入主分支、打 tag / 发版、部署、任务收口、删 worktree、写外部 tracker |
| 准备帮你做 | 本机、可逆、结论唯一的低风险动作（打包确认） | 遗留缺口记入台账、证据落盘、停掉本会话启动的本地临时服务、临时产物归位、落点唯一的坑候选写入 wiki |
| 顺手记下的遗留（这次不做） | 超出本次目标，或需要审美、产品、范围判断 | 旧 bug、技术债、过时文档、环境隐患、后续优化想法 |

提交属于用户点名才做的动作，始终归入「需要你拍板」；范围清楚时把推荐提交范围放首位。只有完全没有任何收尾动作和遗留时，才直接告知可以结束。

## 2. 排序与提问规则

按依赖排序，同一发现只出现一次：

1. 补验或修复当前目标的缺口（未通过或跳过时，第二轮必须如实说明仍未完成）。
2. 提交本地改动。
3. 推送分支并提 MR/PR，或按仓库规则合入主分支。
4. 命中项目发布或部署信号时确认是否打 tag、发版或部署（分题写清版本、渠道与目标环境）。
5. 任务收口（如 `taskrail` `close`）与现场清理（临时服务、worktree）。
6. 缺口记账与知识沉淀。
7. 衍生任务与外部动作。

提问规则：

- 每项一题，给 2–3 个选项；推荐项放首位，标「推荐」并附一句白话理由。
- 题干脱离上下文也能看懂，写清对象、范围和目标分支/环境。
- 同类低风险项可合成一题；外部或不可逆动作一项一题，授权互不外延（选了提交不等于授权 push，选了合入不等于授权打 tag / 发版或部署，打 tag / 发版不等于授权部署）。
- 宿主有结构化提问工具时，把「需要你拍板」直接放进提问工具，正文只留现状摘要与其余区块，不重复列选项。

## 3. 遗留缺口记账落点

缺口记账归入「准备帮你做」，确认后按执行时的任务状态取第一个可用落点（本轮先收口的任务按已收口处理）：

1. 任务未收口：写入 `context/current.md` 的「未决问题」表，`解决形式` 写「另开任务」或「不纳入」。
2. 任务已收口或已归档：在 SUMMARY「剩余风险与后续项」末尾追加一行，注明来源与证据；只追加，不动原文其余部分。
3. 已有 Issue 等 tracker：写入属外部动作，归入「需要你拍板」单独一题；先检索查重，已有则补充证据与来源。
4. 都没有：留在第二轮汇报里，不新建额外文件。

缺口记账不新建任务或子任务；只有用户点名「另开任务」时，才路由到 `taskrail` 或已有 tracker，并附问题、来源、证据、影响、复现方式（如有）、建议判据与相关路径（证据不足标为待查证）。

## 4. 知识沉淀分流

只沉淀跨任务仍有价值、现有文档尚未表达的内容；先找既有落点并去重，没有新经验就不硬写复盘：

| 内容 | 优先落点 |
| --- | --- |
| 当前行为、命令、持续约束 | 项目 README、AGENTS 或既有现行文档 |
| 架构与业务流程的代码映射 | `project-atlas` |
| 关键取舍与术语 | 项目已有 ADR / glossary 机制 |
| 可复用经验、踩坑、操作台账 | 既有知识库或 `wiki-data`，保留来源、置信度与时效 |
| 反复出现且通用的 skill 改进 | `skill-upgrader`；单次失败先留作经验 |
| 任务特例与本次认知更正 | 当前任务 SUMMARY；无任务机制时留在交接中 |

操作台账只记录有追溯价值的动作、环境、结果、影响和回滚方式，不复制普通命令流水。

## 5. 说人话示例与反例

### 第一轮示例（确认前，半屏内看完）

```text
改动已跑过测试，还差最后两步收尾：

需要你拍板
1. feat/export 分支有 3 个提交还没合回 main：推荐推送并提 MR（squash 合入），因为 main 开着 CI；还是先不合，留着本地分支？
2. 清理本次的临时 worktree（无未提交改动）：推荐确认后删掉；还是先留着？

准备帮你做（确认后一起执行）
- 停掉本会话启动的本地 dev 服务。
- 把下面这条遗留记到 context/current.md。

顺手记下的遗留（这次不做）
- 旧导出接口缺空值校验 → 记进未决问题，后续单开任务。

回复「按推荐做」或挑着改，我就开始执行。
```

### 第二轮示例（执行后）

```text
可以收工了。

- 已推送 feat/export 并提好 MR（!42），等 CI 通过即可合并。
- 已停掉本地 dev 服务，删掉了临时 worktree。
- 遗留的旧接口空值校验已记入 context/current.md。
```

### 反例

- 未等用户确认就直接改文件、写 wiki、停服务或删 worktree。
- 代码开发完停在特性分支，工作区干净就直接说“可以结束了”，漏掉推送与提 MR/PR。
- 满屏内部词（`criterion`、`落点`、`建议处置`、`恢复入口`、`按选择跳过`）或用长箭头把五六项信息硬拼成一行。
- 正文列一遍长选项，结构化提问工具里又原样再问一遍。
- 单列一段「已核对事实」复述验证流水，或为凑格式生成额外报告文件。
- 把多个外部动作合成一题，或用提交的选择顶替 push / 合入授权。
- 项目命中发布/部署信号却漏查是否打 tag、发版或部署，或把发版与部署、不同目标环境合成一题。
