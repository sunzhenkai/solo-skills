# 分支合入与提 MR/PR 细则

本次会话有代码改动、且处于非默认分支（或本地默认分支领先远端默认分支）时，必须把「推送并提 MR/PR 或合入主分支」纳入收尾检查，不因工作区干净而跳过。

## 1. 只读核对

给出推荐前，先查清以下现场事实（能查到的不拿去问）：

- 若本次涉及多个仓库或 worktree，逐仓核对以下各项，避免只收了当前仓而漏掉关联仓；
- 当前分支（source）、目标默认分支（target）与远端 tracking 状态；
- 是否有未推送提交、相对 target 的提交数与提交结构（多个 WIP 还是有边界的独立提交）；
- 是否已有指向 target 的 MR / PR，以及它的 CI 与评审状态；
- 仓库分支保护规则、历史合入方式（squash / merge commit / rebase merge）；
- 用户习惯：只采用本次明确选择或已确认的长期偏好，不从单次历史猜测。

目标分支或强制规则不明时先查证。

## 2. 推荐裁决

按以下优先级裁决，给出**一个主推荐**，不只罗列选项：

> **仓库硬规则与分支保护 > 用户本次明确选择 > 已确认的长期习惯 > 仓库历史惯例 > 提交结构**

推荐需同时说明「走什么通道」与「怎么处理历史」（例如 `推送并提 MR（squash 合入）`）：

- **已有 MR / PR**：优先沿用并核对 CI / 评审状态，不重复创建。
- **尚无 MR / PR，且仓库有分支保护、需要评审 / CI 或共享远端**：推荐「推送并提 MR / PR」。
- **直接合入默认分支**：仅在仓库规则允许且符合长期习惯时推荐；合入共享主分支仍需单独确认，且合并授权不自动包含 push。
- **历史处理方式**：
  - 多个属于同一逻辑改动的 WIP 提交 → 推荐 `squash`；
  - 多个各自独立且有意保留边界的提交 → 推荐 `merge commit`；
  - 仓库强制线性历史 → 推荐 `rebase merge`（硬规则优先于个人偏好）。

## 3. 确认后落地

用户确认「推送并提 MR / PR」后，按以下顺序落地，不只停在口头建议：

1. **推送分支**：若当前分支尚未推送或落后本地 HEAD，先按 `commit-push` 的安全默认执行推送（有 `grepom` 时经 `grepom push` 扫密钥）。
2. **创建 MR / PR**：优先调用 `repo-manager` 或宿主已装 CLI（GitHub 用 `gh pr create`，GitLab 用 `glab mr create`）：
   - 明确指定目标默认分支（`--base` / `--target-branch`）；
   - 标题简明概括本次改动，正文附改动摘要与本次实际验证结果；
   - 若仓库要求或用户选定 squash，顺手开启 squash 选项（如支持）。
3. **汇报状态**：若 MR / PR 已创建但尚未合入，在第二轮将其归为外部等待项，写清链接、CI 与评审状态、是否开启自动合并以及是否需要用户回来点击合入；若用户选择暂不合入或跳过推送，如实写明「代码留在本地/特性分支，尚未合入主分支」，并保留对应 worktree，不急于清理。
