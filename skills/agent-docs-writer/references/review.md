# 评审 agent 文档

在 `review` 路径使用本细则。评审保持只读，结论锚定文本和已观察行为，避免只给“更清晰”“更简洁”之类无法执行的评价。

## 1. 建立评审基线

读取目标正文、frontmatter、直接命中的 references，以及用户报告的触发或执行症状。需要判断命令真实性时，再读取对应项目配置。

区分三类证据：

- **事实**：文件内容、实际命令结果、可复现的触发或执行记录。
- **推断**：由文本结构推导出的风险，说明推理依据。
- **未知**：缺少运行时、案例或上下文，列出需要补充的证据。

## 2. 按行为维度检查

### 发现与路由

- description 是否同时表达能力和真实触发分支。
- 近似请求是否有明确归属，相邻 Skill 的职责是否重叠。
- reference 指针是否说明内容与加载条件，必需材料是否藏在弱指针之后。

### 执行与完成

- 步骤是否按实际工作顺序排列，每步是否能判断完成。
- 条件是否可观察，默认方案是否明确，输出形状是否可直接遵循。
- 验证是否覆盖用户场景，完成标准是否要求必要而充分的检查。

### 信息与维护

- 每次运行都需要的内容是否在主文件，分支细节是否按需披露。
- 同一概念的定义、规则和注意事项是否放在一起。
- 同一含义是否有多个权威来源，配置事实是否被复制成容易过期的缓存。
- 句子是否实际改变 agent 行为，是否存在膨胀、沉积或无操作指令。

### 仓库指令专项检查

- 命令、路径和目录职责是否有现场证据。
- 根目录与嵌套文件的作用域是否清楚。
- 安全边界是否配有可执行的安全默认路径。

## 3. 输出发现

按影响排序，每项包含：

```text
[级别] 简短结论
位置：<文件>:<行或章节>
证据：观察到的文本或行为
影响：会导致什么错误触发、执行偏差或维护问题
建议：可检查的目标行为或最小修改方向
```

级别使用 `high` / `medium` / `low`：high 表示会稳定导致错误行为或安全问题，medium 表示常见场景明显受损，low 表示局部可维护性问题。没有证据支撑的猜想放入“待验证”，不计为已确认发现。

完成标志：每项发现都能定位、解释影响并转化为可验收动作；总结同时说明已验证范围和评审盲区。

用户随后要求修复时，`AGENTS.md` / `CLAUDE.md` 进入 `instructions` 路径；已有 Skill 交给 `skill-upgrader`，并携带本次发现作为输入。
