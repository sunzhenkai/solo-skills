# 从零创建 Skill

仅在 `skill` 路径使用本细则。目标是沉淀一类任务的可复用方法，单次任务的解决记录仍留在原工作区。

## 1. 提取能力契约

先从当前对话和真实执行中提取：

- 能力：agent 完成后能够做什么。
- 触发：哪些用户意图或现场分支需要这套方法，每个分支使用什么关键词。
- 输入与输出：必要材料、产物形态和使用者。
- 方法：已验证的步骤、默认选择、判断条件与异常处理。
- 验收：哪些结果可由命令或断言检查，哪些需要人工判断。

优先采用真实任务中的有效步骤和用户纠正。只有通用最佳实践而缺少具体经验时，把它标为待验证假设，通过后续案例补充证据。

完成标志：每个计划中的触发分支都能映射到一段实际方法或明确的待验证项。

## 2. 设计最小结构

以目标仓库的 Skill 约定为准。通常从单个 `SKILL.md` 开始，按实际需要增加资源：

```text
<skill-name>/
├── SKILL.md
├── references/   # 仅部分分支需要的细则
├── scripts/      # 重复且需要确定性的操作
├── assets/       # 输出所需的模板或资源
├── tests/        # 项目已有测试约定时添加
└── evals/        # 可评审的行为案例
```

只创建已有内容的文件和目录。发现执行中反复重写相同逻辑时，再把该逻辑提炼为脚本；一次性操作保留为指令。

## 3. 写触发与正文

Frontmatter 遵循目标环境规范；名称与目录保持一致。description 使用正向的 WHAT + WHEN，关键词前置，每个真实分支有触发条件，与相邻 Skill 的边界放入正文。

正文按执行顺序组织：

1. 说明能力契约和路径选择。
2. 写出共用步骤，每步以可观察结果收尾。
3. 在分支入口直接链接对应 reference，并写明何时读取。
4. 需要固定输出形状时给出模板；需要稳定判断时给出条件、默认方案和例子。
5. 写明验证方式与最终交付内容。

解释约束存在的原因，让 agent 能在合理变体中作出判断。脆弱操作使用精确步骤，开放任务保留选择空间。

完成标志：新读者只按正文和命中的 references 就能执行，无需寻找未声明的背景材料。

## 4. 验证触发与执行

先运行目标项目已有的格式、链接和文本契约检查，再准备至少三个真实案例：

- 一个核心场景，覆盖主要能力。
- 一个边界或变体场景，检查条件与分支。
- 一个近似场景，检查触发范围或相邻 Skill 路由。

每个案例写清输入、预期行为和可检查断言。客观产出优先使用脚本或明确断言；风格、设计等主观质量由人评审。

条件允许时，在独立上下文中比较使用 Skill 与未使用 Skill 的结果，并检查执行轨迹是否出现无效步骤、遗漏或过度触发。只完成静态检查时，交付中写明“尚未独立执行行为案例”。

根据证据做一次收敛：修复导致失败的最小内容，删除未改变行为的句子，再运行受影响检查。单次特例只进入待验证项，反复出现的模式才提炼为通用规则。

完成标志：核心与边界案例有结果，近似场景路由正确，所有已运行检查均通过或附有失败原因。
