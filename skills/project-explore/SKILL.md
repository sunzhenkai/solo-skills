# 项目探索

使用此技能对一个或多个仓库建立可靠且有边界的理解。将**理解**与**实现**分开：先检查并解释；探索期间不得修改源代码、配置、基础设施或外部系统。

## 操作假设

将以下内容视为可配置的占位符，而不是固定路径：

- `REPO_ROOT`：包含一个或多个仓库的目录。
- `ATLAS_ROOT`：可选，已有 project-atlas 的根目录。
- `WIKI_ROOT`：可选，已有 wiki-data 工作区的根目录。

如果工作区使用了不同的名称，应从仓库根目录中发现这些名称，并简要说明映射关系。绝不要臆造组织特定的默认值。本 skill 不维护自己的知识目录。

## 阶段选择

支持以下阶段。如果用户没有指定阶段，则推断最有把握的阶段，并用一行说明该推断。

| 阶段 | 用途 | 默认写入行为 | 做完的标志 |
|---|---|---|---|
| `ask` | 优先基于现有知识回答聚焦的行为、术语或规则问题。 | 只读 | 回答的每个结论都带路径 / 符号出处，未知项已标明 |
| `explore` | 追踪实现路径、依赖关系、数据流或变更影响。 | 只读 | ExplorationBrief 五部分齐全，调用链或影响面每一跳有证据 |
| `archive` | 将保存需求分类并交接给 Atlas、wiki 或两者。 | 只读；按需交接 | 持久化计划已给出；获批部分由对应 skill 完成并返回回执 |
| `ingest` | 将来源、决策和经验交给 wiki-data，混合材料先拆出现行系统内容。 | 只读；按需交接 | 保存范围明确，Atlas/wiki 分别完成各自流程 |
| `project` | 查询或建立项目理解入口。 | 只读；按需交接 | 已读取 Atlas，或已将建立需求交给 project-atlas |

如果请求在两个阶段之间存在歧义，应提供两种解释，而不是悄悄执行写入或交接。如果用户要求实现或编辑代码，则停在探索边界，并交接给仓库的实现工作流。

当前系统说明交给 `project-atlas`，决策背景、经验、台账和跨项目知识交给 `wiki-data`。本 skill 只取证和路由，不创建独立 project profile，也不在下游 skill 缺失时自行落盘。

## 证据与安全规则

1. **在检查源代码前优先使用已有知识。** 从 Atlas、wiki、索引、规范和架构笔记开始。
2. **采用渐进式披露。** 只读取回答问题所需的证据；默认不要扫描整个工作区。
3. **让结论有证据支撑。** 引用仓库相对路径、符号、配置键、接口或明确的调用关系。
4. **保持探索只读。** 不要编辑文件、创建提交、切换分支、安装依赖、运行破坏性命令或调用具备写入能力的 API。
5. **外部变更必须经过确认。** 任何数据库、云服务、集群、部署、配置服务或工单/文档变更，都需要单独且明确的确认门槛。
6. **隐去机密信息。** 绝不要输出凭据、令牌、私钥、个人联系方式、内部主机名或敏感载荷。将它们替换为 `<REDACTED>`，仅保留必要的结构。
7. **不要过度断言。** 区分已观察到的事实、强推断、假设和未知信息。
8. **保护无关工作。** 不要重新格式化、重新生成或“清理”请求文档范围之外的文件。

## 渐进式加载协议

按以下层级顺序使用，并在问题得到回答后立即停止：

- **L0 — 路由：** Atlas 入口与状态、wiki 索引、仓库索引、工作区 README 或文档索引。
- **L1 — 概览：** 相关 Atlas 页面、仓库 README、模块地图、包清单、服务目录或顶层规范。
- **L2 — 细节：** 最小的相关 wiki 页面、设计笔记、配置文档、关系图、测试或源代码文件集合。
- **L3 — 证据追踪：** 针对符号、调用链、数据流或影响分析的定向源代码检查。

除非有明确且具体的理由，否则 L0–L2 合计预加载文件数保持在**六个或更少**；如超过，应在报告中说明例外原因。在进行广泛内容搜索前，先使用索引或符号搜索。除非与问题直接相关，否则避免读取生成文件、第三方 vendored 依赖、构建产物和无关历史记录。

### 证据层级

在注意冲突的同时，按以下顺序优先采用证据：

1. 当前源代码和可执行测试。
2. 已复核且未过期的 Atlas 当前系统说明。
3. 版本化的规范和设计文档。
4. wiki 中带来源、置信度和时效的背景、决策与经验。
5. 用户提供的陈述和历史笔记。
6. 仅基于命名或惯例的猜测。

当来源相互矛盾时，应报告冲突，并解释对于当前问题哪个来源更具权威性。Atlas 过期或未覆盖时进行有边界的源码核实；query 本身不自动更新 Atlas 或 wiki。

## 各阶段详情

各阶段（`ask` / `explore` / `archive` / `ingest` / `project`）的步骤、输出格式和持久化建议：**进入阶段后先读** [references/phases.md](references/phases.md) 对应小节，不预加载其它阶段。

## 持久化交接

- `archive` 先区分当前系统说明、长期知识、两者或无需保存，再给出目标、证据和保存价值。
- 混合内容先完成 Atlas，再由 `wiki-data` 摄入决策背景、经验或台账；两个工作区分别遵守各自的写盘确认。
- `ingest` 使用 wiki-data 的来源、置信度、时效、隐私和 lint 契约。
- `project` 使用 Atlas 的 L0、领域页和 `status / init` 契约，不建立另一套仓库卡片。
- 交接只携带摘要、证据和未知项，不复制完整源文件。

用户提出“分析”“追踪”“理解”或“审查”请求，并不代表授权编辑源代码或持久化文档。

## 触发示例

- “这个配置标志控制什么？” → `ask`
- “追踪从 HTTP 处理器到持久化的请求流程，并告诉我超时变更会影响什么。” → `explore`
- “把我们刚找到的调用链记录下来。” → `archive`
- “保留这些笔记作为项目背景，同时保留不确定性。” → `ingest`
- “为这个仓库建立可持续维护的项目入口。” → `project`

## 经验回灌

安装到各 agent 目录的 skill 是字节复制镜像：往 skill 目录内写的内容会在下次同步时丢失，运行时只读是仓库纪律。因此：

- 探索产物与可复用教训一律落**工作区**，由 project-atlas、wiki-data 或任务台账按职责保存，不落本 skill 目录。
- 需要改进本 skill 正文时，在**源仓**走显式流程：来自真实执行经验的改动委托 `skill-upgrader` 的 `evolve` 模式（先提案、经用户确认再写 `evolutions/`）；结构或规则的显式修订走 `skill-upgrader` 的 update 模式（`patches/` 审计）。未展示 Proposal 并获用户确认前，不改生产正文。
- 单次失败或单次用户纠正不足以改 skill；可复用、跨任务稳定出现的规律才够门槛。
