# 各阶段流程与输出模板

## 阶段：`ask`

用于回答聚焦问题，例如“这个选项是什么？”“这条规则在哪里定义？”或“这个组件负责什么？”。

### 流程

1. 解析主题、仓库、时间范围以及所需的详细程度。
2. 加载 L0–L2 知识；当前系统问题先看 Atlas 覆盖与 `stale` 状态，背景问题再查 wiki。
3. 如果已有知识足够且时效明确，直接回答并附出来源。
4. 如果 Atlas 过期、未覆盖或需要追踪源代码，建议使用 `explore`；只有当用户明确希望快速回答且证据范围可以受限时，才执行小范围的有边界查询。
5. 说明置信度和证据缺口；query 不自动更新 Atlas 或 wiki。

### 输出

```markdown
## 答案
<用一到三句话给出结论>

## 证据
- `<仓库相对路径>` — `<章节、符号或关系>`
- `<Atlas/wiki 页面>` — `<支持性要点及其时效>`

### 摘要与置信度
- **摘要：** <简短重述>
- **置信度：** high | medium | low — <原因>
```

保持回答简短。只有在升级处理或记录文档有帮助时，才添加下一步建议。

## 阶段：`explore`

用于项目结构调查、调用链追踪、仓库导览、依赖分析、数据流分析、回归风险或变更影响评估。探索不是实现。

### 流程

1. **界定任务。** 记录问题、范围、目标行为和成功条件。
2. **识别仓库。** 根据明确路径、仓库名称或工作区索引解析出唯一仓库。如果有多个候选项匹配，应列出它们，不要自行猜测。
3. **加载上下文。** 读取相关 Atlas/wiki 与 L0–L2 材料，然后识别可能的入口点、边界和输出。
4. **绘制路径。** 沿着符号和接口追踪最小且有用的链路：入口点 → 校验/分发 → 核心逻辑 → 副作用/输出。
5. **检查支持性证据。** 检查相关测试、配置、schema、错误处理和相邻调用方。
6. **评估影响。** 区分直接调用方、间接消费者、配置或数据契约依赖，以及可能的回归面。
7. **记录不确定性。** 列出未经验证的假设、动态/基于反射的边、生成代码和缺失的测试。
8. **在有用的边界停止。** 不要仅仅为了让地图看起来完整，就继续进入无关模块。

### 仓库检查顺序

根据仓库使用的语言和布局进行调整，默认采用以下顺序：

1. Atlas 相关页面及状态、顶层 README 和贡献/开发者文档。
2. 构建或包清单，以及工作区/模块定义。
3. 目录/模块地图和服务边界。
4. 已命名的入口点、路由、命令、处理器或公共 API。
5. 核心符号及其直接调用方/被调用方。
6. 约束行为的测试、schema、配置和部署元数据。

### 搜索规范

- 在搜索通用术语前，先搜索精确符号、路由名称、配置键、错误码和接口名称。
- 在可用时，优先使用结构化或理解符号的搜索。
- 通过仓库、目录、文件类型和明确的搜索模式限制广泛搜索。
- 总结发现，不要粘贴大段源代码。
- 只有当问题涉及意图、回归、归属或时间点时，才检查历史记录；历史查询应保持范围狭窄。

### 有边界的委派

当有只读子代理或并行工作器可用时，只委派相互独立且范围明确的侦察任务：

- `repo-scout`：阅读 Atlas 和概览文档并定位可能的入口点。
- `code-tracer`：从已知入口点追踪一条指定路径。
- `impact-scout`：识别调用方、消费者、测试和配置依赖。

为每个工作器指定一个仓库和一个问题。要求提供紧凑的简报，而不是源代码转储：

```markdown
## ExplorationBrief
- repository: `<相对路径>`
- entries: [`<路径:符号> — <职责>`]
- call_chain: [`A -> B -> C`]
- findings: [`<路径> — <有证据支撑的要点>`]
- risks: [`<风险或未发现风险>`]
- unknowns: [`<未经验证的要点>`]
- files_read: <数量>
```

默认最多使用两个并行工作器。不要委派一个在本地取得任何有用进展之前就必须等待其结果的任务。如果没有子代理能力，则在本地应用相同的范围和输出约束。

### 输出：五部分探索报告

```markdown
## 任务理解
- **问题：** <调查了什么>
- **范围：** <包含和排除的仓库/模块/文件>

## 代码地图
1. `<路径:符号>` — <作用>
2. `<路径:符号>` — <作用>
3. `<路径:符号>` — <作用>

**调用/数据路径：** `<A> -> <B> -> <C>`

## 发现与风险
- <有证据支撑的发现>
- <直接或间接影响>
- <风险、缺失测试或不确定性>

## 选项或下一步
- <只读后续操作、验证或实现交接>

## 证据与审计
- `<路径>` — <相关章节/符号及其重要性>
- 读取文件数：<数量>；使用工作器数：<数量或无>
- 写入/外部变更：无

### 摘要与置信度
- **摘要：** <用一到两句话回答>
- **置信度：** high | medium | low — <依据和剩余缺口>
```

当某个类别没有结果时，明确使用“未发现”。不要因为某个假设符合命名方式，就将其当作事实。

探索结果有持久化价值时，可追加以下部分；它只是交接建议，不触发写入：

```markdown
## 持久化建议
- Atlas：
  - 页面：<建议新增或复核的页面；无则写无>
  - 依据：<路径:符号>
  - 原因：<为什么值得长期维护>
- Wiki：
  - 主题：<候选主题；无则写无>
  - 类型：<experience / concept / ledger / ...>
  - 保存价值：<后续如何复用>
- 不纳入：<一次性细节或证据不足项>
```

## 阶段：`archive`

仅在用户要求保存探索结果时使用。本阶段生成持久化计划并交接，不直接写文档。

1. 将候选内容分为当前系统说明、长期知识、两者或无需保存。
2. 只读检查已有 Atlas 页面与状态、wiki 候选页和来源，避免重复交接。
3. 给出持久化计划：目标 skill、页面或主题、动作、证据、保存价值、置信度、未知项和不纳入项。
4. 当前系统说明交给 `project-atlas`；决策背景、备选方案、经验、台账和跨项目知识交给 `wiki-data`。
5. 混合内容先完成 Atlas，再按已确认列表交给 wiki-data；两个工作区分别执行写盘确认。
6. 返回下游回执；用户尚未确认写入时只交付计划。

绝不要将完整源文件复制到持久化笔记中。应保留源代码链接和摘要。如果工作区已有既定的文档 schema，应遵循它，而不是引入相互竞争的新 schema。标记矛盾和未知信息，不要悄悄替其解决。在任何大范围或不可逆重写之前，展示拟写入目标和摘要。

## 阶段：`ingest`

当用户提供的笔记、决策或领域知识需要保存时使用。

1. 保留用户原意，区分用户事实、代理解释和未验证假设。
2. 将现行架构、业务流程和规则拆给 `project-atlas`，其余来源、决策、经验和台账交给 `wiki-data`。
3. 混合材料先完成 Atlas，再由 wiki-data 按归档列表摄入；本阶段不直接创建来源页或业务页。
4. 沿用 wiki-data 的来源、置信度、时效、隐私、交叉引用和 lint 契约。
5. 标记矛盾和未知信息，不要悄悄替其解决。

## 阶段：`project`

用于查询或建立可持续维护的项目理解入口，不创建独立 profile。

1. 已有 Atlas 时，读取 `status`、L0 和与问题相关的页面；回答附具体页面与源码映射。
2. 没有 Atlas 且用户只要求一次性概览时，用 `ask` 或 `explore` 给出 Brief，不创建仓库卡片。
3. 用户要求持久化项目入口时，将范围和已有证据交给 `project-atlas`，由其执行 `init` 确认、首批页面建立和验证。
4. Atlas 的回执应包含根目录、已覆盖页面、`draft` 范围和过期状态；本阶段不另存 profile 或索引。
