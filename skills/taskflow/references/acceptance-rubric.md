# 验收 rubric

复杂交付的最终验收按本文件评分。评分是给结论用的，不代替 checkbox 进度；进度仍只认 checkbox。

## 评分主体与顺序

- 先交证据，再由对应岗位打分；实现者自评只作输入，不算通过线。
- 打分 MUST 经 `role-based-reviewer` 结构化调用（`mode=review` + 完整 `roles=` + 审阅边界；边界列举以 task-confirm 审阅节为准：完成判据、质量画像 / 角色底线、显式降级原文、门包与运行态证据、审与不审）。退普通 subagent 须写明不可用原因，否则按 task-confirm 退出点「评审降级未记录」不放行。
- 角色由交付类别门包（[../../task-confirm/references/gate-packs.md](../../task-confirm/references/gate-packs.md)）确定，不得少于该表「必载评审」：功能闭环与画像一致性由 `product` 评；UI/UX 由 `design` 评；工程质量由 `engineer` 评；其余类别按其门包。
- 评分先套门包：**可自动化门**任一失败 → 对应维度不得 ≥2.5（UI 类别为 UI/UX 维度）；**未覆盖条目**按显式降级计，A 类未确认不得计为通过。
- Web UI：可自动化门对齐 Active Instance validate / `scan_design_constraints`（或等价）与门包 token/无障碍/状态/结构断言；运行态优先 `ui-template-apply` Phase 8 current-build 证据；主观项（视觉层级等）MUST 指到 Gallery 或 `core/tokens.yaml` 可指认件，否则只记 Suggestion。
- 复杂档交付验收 SHOULD 异源（`model=` 与实现者不同，或 `endpoint=` 走名册）。
- 三方结论不一致时保留各自意见，按影响面决定优先级，不取平均掩盖分歧。

## 五维评分

| 维度 | 3 分 | 2 分 | 通过线 |
|------|------|------|--------|
| 功能闭环 | 主流程全通，失败路径可用 | 主流程通但有未处理边界 | ≥2 |
| UI/UX | 信息架构、视觉层级、关键状态、反馈、无障碍、响应式均可检查 | 可用但个别子项不足 | ≥2 |
| 工程质量 | 测试、错误边界、启动说明齐 | 测试或启动说明有缺口 | ≥2 |
| 画像一致性 | 实现逐条对得上质量画像 | 只有已确认且记录的降级 | 无未确认偏差 |
| 证据 | 截图或导出日志 + 可复现命令 | 证据部分缺失 | 全部齐 |

全量通过线：五维均 ≥2，UI/UX 六子项均值 ≥2.5，任一子项为 0 不通过。

## UI/UX 六子项

| 子项 | 关注点 |
|------|--------|
| 信息架构 | 入口、层级、导航与信息组织是否清楚 |
| 视觉层级 | 主次、间距、排版、对比是否成体系 |
| 关键状态 | 空、加载、错误、无权限、无结果是否都有交代 |
| 反馈 | 操作成功/失败/进行中有明确且及时的反馈 |
| 无障碍 | 焦点管理、键盘可达、对比度、语义与替代文本 |
| 响应式 | 常见窄屏与桌面布局都能用，不靠压缩硬塞 |

UI/UX 得分是六个子项的平均分，任一子项为 0 则不通过，即使均值达标。

## Web UI 证据前置

交付类别为 Web UI 时，UI/UX 维度评分前必须已有（任一缺失 UI/UX 记 0，不通过）：

- 最新代码上的 `task-confirm/scripts/ui_evidence_check.py` `report.json`，exit 0（多视口截图、axe WCAG 2.2 AA、焦点走查、四态）；
- design 评审文件：`roles: design`、reviewer ≠ implementer、指向该 report，`--validate-review` exit 0。

六子项打分由评审文件给出并引用 report 中的截图 / 违规条目；实现者自评与「源码已修订」不计分。

## 目标为「优秀 UI/UX」时

- 设计底线逐条通过。
- 截图评审无 Major 级问题。
- 不满足就按实测分数记录，不用「已经不错了」放行。

## 与画像、rubric 的关系

- 质量画像定义这个任务应该做到什么；rubric 定义做成什么样算过关。
- 画像字段缺失、底线没有验证方式时，先补画像，不用 rubric 评分顶替。
- 有降级时，A 类先经用户确认再评分；B 类可按 `provisional` 临时确认的范围评分并标注「待追认」；未确认（A 类 `pending`，或 B 类既无确认也无 `provisional`）不得计为通过。

## 记录

- 每维写分数、证据与扣分理由，不写「整体良好」这类无法复核的结论。
- 分数与证据写进 driver `proposal.md` 的验证记录，或任务约定的验收记录位置。
