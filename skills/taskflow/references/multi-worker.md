# 多 worker 并行（附录）

默认串行 + checkbox。只有宿主有多 agent 能力、且有 ≥2 个**无未完成依赖、改动范围不重叠**的单位时才读本文件。并行只改变执行方式，完成度仍只认 checkbox。

## 可以并行什么

| 层 | 可以并行 | 必须串行 |
|----|----------|----------|
| 子 change | 落在不同修改仓，或已确认改动文件不重叠 | 可能改同一批文件或互相依赖契约；准备段建 worktree；收尾段回归 / 回填 / 提交 / 归档 |
| 同一 change 的 checkbox | 互不依赖且文件不重叠 | 有先后依赖、共享文件、或卡在用户决策上 |

每个 worker 只领一个单位：在其 planning root 下执行并给出 change name；只改自己范围内的代码与自己的 checkbox；不勾 driver 编排项；不写 `建议` / `排除` 仓。主会话负责派发、汇总、处理冲突。同一任务的 worker 共用 `worktrees/{task}`（Driver 协议），靠改动文件不重叠隔离。worker 失败不是整轮结束的理由。

## 派发前

- **先冻结共享面**：接口、类型、共享组件、目录与命名先落成仓库内的契约文件，再并行。
- **样板先行**：新类型的交付（新页面族、新服务形态）先只派一个样板切片做全、过评审，再让其余切片照它铺开。

## 飞行中

- **同类失败升级**：≥2 个 worker 报同一类失败，按契约或计划缺陷处理：停并行、回 design 修契约，再重新派发。
- **改共享面先广播**：主会话改 worker 会读的共享文件前，先通知改动点和影响面；动手写文件前核对它不在任何在跑 worker 的范围内。

## 实现者输入

正常交付给：需求原文与负责范围、判据与相关验收要求、运行约束、必要的既有契约。不必给完整评审意见与其它切片细节。只有任务显式标记 benchmark / regression 时才盲测复跑：只给同一份需求原文与运行约束，不给验收清单，不追加事后提示。
