# 交付质量闭环

本文件规定复杂交付怎么验证，不规定做什么功能；进度仍只认 checkbox，本文件不建第二份账本。

## 什么时候用

- 复杂交付（taskflow driver 编排的任务）在收尾段执行。
- 单个子 change 的改动面较大、或跨前后端与数据层时，也可在子 change 内先跑一轮窄切片。

## 三层验证

| 层 | 目的 | 什么时候跑 |
|----|------|------------|
| 静态门 | 规则/契约是否落地，秒级到分钟级 | 每次改动规则或契约之后 |
| 窄切片 | 用一个最小闭环暴露流程与实现缺口 | 首次实现或大改之后 |
| 全链路 | 跨切片一致性、数据层、导航与整体验收 | 收尾段，只跑一次 |

窄切片先行：不要一上来铺全量功能，先跑通一个能从头走到尾的最小闭环，再扩展。

**契约前置**：首次实现或大改之前，先冻结共享面契约（接口、类型、primitive、目录与命名、样板切片）并落成仓库内的契约文件；并行派发只允许发生在契约冻结之后；冻结后仍需变更时走 SKILL.md「并行执行」的共享面广播纪律。Web UI：共享面契约 = 交付项目根 frozen `design-system/v1` Active Instance（三条 digest）；页面实现走 `ui-template-apply`，不另起散文契约。

**旗舰切片**：交付类别命中 [../../taskrail/references/gate-packs.md](../../taskrail/references/gate-packs.md) 门包、且属首次实现或大改（无可复用样板）时，先只做一个旗舰切片——把该类交付的代表面做到全量（含门包要求的可自动化门与运行态证据），经门包「必载专家能力」评审通过后才铺开；旗舰切片同时是其余切片的复制样板。无样板可循（新交付类别、新页面族）时不得直接并行。Web UI 旗舰切片经 `ui-template-apply`，证据优先 Phase 8 + Gallery。

**门包叠加**：命中门包的类别，本文件三层之上再叠加门包条目（可自动化门 / 运行态证据 / 主观项）；门包条目未覆盖的一律按 taskrail 确认协议「未覆盖即降级」登记，不得以「看起来没问题」通过。Web UI 静态门优先 `check_active_instance.py validate` 与 `scan_design_constraints.py`（或项目约定等价）。

## 窄切片怎么做

1. 从需求原文里挑 1-3 个核心闭环，保证每个都有入口、动作与结束状态。
2. 只实现这些闭环所需的真实路径——可以少做功能，但不要用假数据、假接口或写死页面冒充打通。
3. 独立跑一遍：按 README 启动、执行自动化测试、抓运行时证据。
4. 记录结果后再决定是否铺开。

窄切片的目标是暴露缺口，不是交作业；它不通过就不进全量。

## 失败三分类

窄切片或全链路失败时，先归因再动手，只治一类病：

| 分类 | 判据 | 处置 |
|------|------|------|
| skill gap | 规则没写清、门禁缺失或指引矛盾，换个任务同样会错 | 改对应 skill，走 `patches/` 协议出可审计 patch |
| implementation bug | 规则正确，实现写错 | 在交付仓修复并补回归测试 |
| acceptance gap | 评分或验收标准本身漏了维度 | 补 rubric / 验收标准，再重验 |

一次失败可能同时命中多类，按上面顺序拆开，分别处置，不要混成一句「再改改」。

## 增量评审

评审不堆在收尾：旗舰切片后必审一次；此后每完成一批切片审一次——批次划分由主会话在实施段开始前声明（写进 driver 验证记录），不得事后追认；门失败修复后重跑受影响层再审。收尾只做全链路与全量门，且不代替增量评审。

每轮评审的产出必须落到 disposition：每个 Blocker / Major 标 `fixed` 或 `accepted-recorded`（含理由与影响面）；无 disposition 的 findings 不得判收敛，也不得回填验收标准。执行器与角色按 [acceptance-rubric.md](acceptance-rubric.md) 与门包表确定。

## 证据

- 每个进入交付目录之外的文件都写绝对路径；项目已有约定临时目录时用那个。
- 至少留：启动命令与输出、自动化测试结果、关键流程运行时证据（截图或导出日志）、失败与修复对照。
- 证据必须与当次代码状态一致；换代码后旧证据作废，重跑受影响部分。
- **状态绑定**：每组证据注明所绑定的产物状态（提交号，或未提交时的 dirty 摘要）；无法绑定的证据不构成通过依据。
- **覆盖边界**：证据必须写清「覆盖了什么、没覆盖什么、为什么」；未覆盖条目按 taskrail 确认协议「未覆盖即降级」登记。
- **工具不可用**：标准证据工具不可用时，写明替代方法与能力边界、重估覆盖度，替代不等于等价通过。
- 不把本机路径、凭据、内部 URL 写进共享 skill 或交付文档。

## 只重跑受影响切片

skill gap 或 implementation bug 修好后：

1. 先重跑直接受影响的那一层（静态门 / 窄切片）。
2. 通过后再跑一次全链路验收。
3. 不做与本次改动无关的全量重跑来「图安心」；预算要留给扩范围。

## 收尾

- 全链路验收通过、证据齐、A 类 `pending` 降级为 0、B 类无未追认 `provisional`（全部 `confirmed`），才回填验收标准；B 类 `provisional` 期间可回填不依赖该项的验收标准。
- 验收评分按 [acceptance-rubric.md](acceptance-rubric.md)。
- 失败未归类、证据缺失、或仍有 A 类未确认降级 / B 类未追认降级时，不勾收尾 checkbox。
