# 质量画像

术语见 [../CONTEXT.md](../CONTEXT.md)。服务于 task-goal 的 Goal 方案，只在复杂档强制：它是完成判据的约束，不是独立文档，也不要求穷举质量标准的全部维度。不做自动评分器——字段是否齐全、底线能否验证，由审阅者按 P 级判定。

## 字段

```text
受众与场景: <谁在什么场景完成什么>
规模与运行假设: <人数、并发、数据量、本地 / 共享 / 生产>
页面/主流程: <3-7 条，每条一个入口到一个结束状态>
角色底线:
  product: <核心工作流、范围外、协作边界>
  design: <视觉方向、关键页面、必备状态、可用性与无障碍底线；质量目标含审美 / 体验等无法用确定性度量完备验收的项时，另写天花板参照集>
  engineer: <数据一致性、并发、错误边界、测试与本地启动证据>
显式降级:
  - 维度: <如持久化方式、实时协作、移动端适配>
    定级: <A 类 | B 类；A=使完成判据不成立或收窄交付面，B=判据与交付面都不缩；拿不准归 A>
    默认期望: <画像其余字段自然推出的要求>
    实际选择: <本次接受的实现>
    原因: <范围或约束>
    回滚说明: <B 类必填：追认否决时撤什么；A 类写「无」>
    确认状态: <confirmed | provisional | pending>
```

- 五个顶层字段都要写；`角色底线` 下的 product、design、engineer 三条一条都不能省。
- 质量目标含审美 / 体验等无法用确定性度量完备验收的项时（典型：UI 观感、文案气质、交互手感），design 底线还须写**天花板参照集**：把「卓越」落到可数的构成件，或列外部参照（作品、规范、既有页面各指到具体件，写清取它哪一点），写在 design 底线里、与其余底线同样可检查。实测指标与地板只声明「不低于」，替代不了参照集；写不出先走退出点「理解不够」，不以「无缺陷」默认收工。
- 主流程 3-7 条。超出 7 条说明范围过大，按「不做的事」收敛，不堆清单。
- 每条底线写成可检查的话：点出页面或状态、并发与数据量假设、以及验证方式（运行、截图、测试、启动步骤）。「高质量」「体验好」「足够健壮」这类形容词不算。
- 某维度确实不适用：写「不适用」加一句原因，不留空，不默默省掉字段。

## UI 交付的 design 底线必须回答

画像覆盖含界面交付时，`角色底线.design` 除视觉方向、关键页面、必备状态外，还必须能用一句话回答四个契约问题；回答不出按「空泛形容词」归 P0，复用缺字段判定。确实不适用写「不适用」加一句原因。

```text
控件密度: <哪些 surface 用常规档、哪些用密集档；同一上下文内是否要求同高>
icon 形态: <是否收敛到单一 icon primitive 及其来源；是否禁止裸字符/emoji 充当 icon>
表单间距: <字段间距与表单收尾间距是否来自 token，而非手写数值>
证据分工: <哪些一致性要求用 DOM/静态断言钉住，哪些必须截图确认>
```

- 四问只约束「底线要写清」，不规定具体取值；取值由设计决定，写清即可。
- 「证据分工」必须写验证方式，与「每条底线带验证方式」同一条纪律。

## 天花板参照集的去向

- 随画像原文快照流到 task-explore、taskflow 与 Stage 7 审阅，作为 design 角色的审阅边界输入；哪件参照用在哪、差在哪，由 design 角色按它出自己的评审意见。
- 参照集不引入新的审阅对象：架构、接口、schema、代码骨架与底层设计不在其内（「缺字段怎么判」末段的「不审」列照旧）。
- 参照集本身写不出，或与完成判据冲突：按缺字段处理——记 P0，走「理解不够」或回画像完善，不改完成判据。

## 与交付标准的分工

复杂档下画像收编交付标准里的三类：验证或测试覆盖、错误与边界行为、运行假设。这三类不再重复写进「交付标准」；「交付标准」只写画像未覆盖的交付面，例如文档与配置等配套更新。简单和中等不写画像，交付标准照旧。

## 显式降级

- 判定看实质，不看措辞：凡比默认期望少交付的都是降级，改名成「技术选型」「本期简化」也一样算。
- 每条降级先定级：**A 类**——使完成判据不成立或收窄交付面；**B 类**——完成判据与交付面都不缩，只是交付方式、顺序或批次的诚实声明。拿不准一律归 A，定级理由写进该项。
- 方案完善阶段一次列出所有已知生产性降级，初始状态一律 `pending`。
- `confirmed` 只有用户能写：点名接受该项、明确说按降级表全部确认、或在用户在场点（真人门、收口）追认。`provisional` 只有 B 类可经审阅收敛写入（临时确认），A 类任何情况下都不许。执行者与审阅者不能把 A 类写成任何已确认态；单独的「继续」不算任何确认。
- A 类仍有 `pending` 时按退出点「降级未确认」停：不开工、不交接。B 类 `pending` 走审阅临时确认，不停机；`provisional` 到用户在场点集中追认——追认改 `confirmed`，否决按该项回滚说明处理后回退出点重定级。
- 实现中发现新的降级：补进降级表并定级，A 类回确认门、B 类走审阅，不静默接受。

## 缺字段怎么判

派审时把完成判据原文、画像原文、显式降级原文一并贴上。缺任一必要字段、字段写成空泛形容词、或核心底线没有验证方式：记 P0，路由写成 `完善中：补质量画像并再审。此阶段不改代码。`，不开工。确实写不出——说不清受众与场景，或主流程完全未知且会改方案——才走退出点「理解不够」。

画像不引入新的审阅对象：架构、接口、schema、代码骨架仍在「不审」列里。写不出某条底线不等于要先做大设计，按上一段判 P0 或走「理解不够」。

## 交接与完成门

- 复杂档交接给 task-explore 时逐字带上画像原文快照，含显式降级表；路径或小节指针只作辅助，不能替代快照。后续设计、子任务的验收标准引用同一份原文。
- 完成门：字段齐全，降级表无 `pending` 且无 `provisional`（B 类已全部追认）；`confirmed` 降级在验证记录里可追踪。
