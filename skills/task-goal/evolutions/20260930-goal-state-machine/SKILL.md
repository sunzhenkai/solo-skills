# Task Goal：goal 执行协议

写给正在执行 goal 的 agent。方案正文自洽：之后的回合只重读已经写下的方案。方案只出现在当轮回复前部，不落文件。完成判据是一条可检查的话，写在方案里，用它判断做完没有。用户已经发出的 goal 原文保持原样。

## 触发

三者任一命中即处在 goal 里，由本协议接管确认与审阅；都不命中则退出，不产方案：

- 消息里看得到 `/goal`。
- 当前有进行中的 goal 且本条消息挂了本 skill。
- 被上游 skill（如 task-delivery、task-explore）以 goal 模式委派。

每轮开头把本条输入对照 [references/state-machine.md](references/state-machine.md) 的「事件」节归到一类，再查网格；无格按「无进展轮」处理。网格与本文件正文或「无进展轮」有出入时，以正文与无进展轮为准。

## 起手：接方案或产方案

- **上游带来方案原文**（典型：task-wizard 的步骤级方案，含完成判据 / 事实 / 假设 / 步骤 / 阻塞点 / 坑 / 不做的事）：跳过产方案，逐字采用，不重新摸底、不改写。复杂档带着质量画像与显式降级原文快照的，同样逐字采用。然后按「外部参照」（复杂档）→「审阅」继续。方案缺完成判据、或判据不是一条可检查的话：不补齐不猜，按自产方案处理，从摸底开始。
- **没有现成方案**：自己做只读摸底（代码 / 文档 / 环境），然后按「正文」产 Goal 方案。方案缺口的处理沿用「审阅」与「退出点」，不向用户列选项。

## 减少确认

凡要向用户确认的决定，含本协议的路由选择和下游 skill 里的确认，都走「审阅」，不列选项。审阅收敛则采纳该处推荐默认并继续。单独「继续」只对退出点造成的 `已停` 无效。详细设计，以及危险操作、线上动作、泄密等退出点，仍停，不交给审阅放行。排查写不出步骤时，推荐走 task-explore，先走审阅；收敛后直接开始，不向用户要这句话。

术语见同目录 `CONTEXT.md`。

状态只允许 `执行中`、`已停`、`已交接`、`已完成`。退出、升档、交接、做完时改写状态与路由，使最后一份方案等于当前状态。

## 不套模板

原因还不清、要先排查的，以及要定接口或架构的详细设计：不套下面的步骤正文，不新增工作。回复仍写出状态 `已停` 与路由。

- 排查：推荐走 task-explore，先走审阅，不向用户要「走 task-explore」。审阅收敛后直接开始。审阅不通过、派不出或没有结论时才 `已停`。
- 详细设计：`已停。本流程不做详细设计。`

## 正文

没有的小节写「无」。交付标准只取与本任务相关的交付面；不确定该不该列的维度，写进「不做的事」，不默默漏掉。质量画像只在复杂档必填：按 [references/quality-profile.md](references/quality-profile.md) 写字段齐全（`角色底线` 三条都要写），不能以「高质量」这类形容词代替；简单和中等写「无」。复杂档把验证或测试覆盖、错误与边界行为、运行假设收进画像，「交付标准」只写画像未覆盖的交付面。缺任一必要字段是 P0，路由写成 `完善中：补质量画像并再审。此阶段不改代码。`，不开工；确实写不出才走退出点「理解不够」。半屏放不下时压缩前提和坑；完成判据、步骤、退出点、方案置信度、状态、路由保留。假设一旦被打穿就会改步骤或完成判据的，不开工，状态写 `已停`，走退出点「理解不够」。

```markdown
# Goal 方案：<任务名>

## 完成判据
<一条可检查的话>

## 质量画像（复杂档必填）
<字段：受众与场景 / 规模与运行假设 / 页面或主流程 / 角色底线（product、design、engineer）/ 显式降级；简单和中等写「无」>

## 交付标准
- <本任务应有的交付面要求；复杂档只写画像未覆盖的项；无则写「无」>

## 前提
- 事实：…
- 假设：…

## 步骤
1. <动作> — 要点：…；验证：…

## 阻塞点
- 无

## 退出点
- 理解不够；阻塞解不开；未点名的危险操作；线上动作；同一验证连败两次；泄密；执行中升档；审阅不通过；审阅派不出；审阅没有结论；评审者未定；降级未确认（复杂档）
- 命中任一标签后把状态改为已停，路由写成需要的授权。单独「继续」不算授权。执行中升档除外：改为已交接，按新档位衔接，不另问路由。危险操作在任务点名后可以做；线上动作与泄密即使任务点名也停。
- 本任务另有：无

## 坑
- 无

## 不做的事
- …

## 方案置信度
<高 / 中 / 低>

## 状态
执行中

## 纪律
- 执行中：路由以「完善中」开头时，只改正方案并再审，不执行步骤里的实现。否则从第一个未验证步骤做。判据成立就改为已完成。
- 已停：只做已经点名的那一件授权。单独「继续」仍停。评审已收敛、且没有命中其他退出点的档位路由，不停在这里。
- 已交接：不重出方案。按路由里的账本继续。账本做完且完成判据成立才改为已完成。
- 收敛后：按档位直接下一跳，不向用户确认路由，不列出「走 task-explore」或「仍按此方案执行」。下游要向用户确认的决定同样走审阅。
- 改步骤：完善中可以改完成判据和步骤。离开完善之后，仅当状态仍是执行中、完成判据不变、档位仍是简单。
- 审阅：按「审阅」节派审、核对和收敛。完善中只改正方案，不改代码。

## 路由
<当前状态的下一跳>
```

## 外部参照

上游方案已含外部参照（task-wizard 复杂档在定稿前做过）：前提里对上的在事实、对不上的在假设，逐字采用，不重做。上游没做、或本协议自产方案时摸底后的档位是复杂：读并做完 [task-wizard 的外部参照](../task-wizard/references/external-precedent.md)（读不到 task-wizard 时按该文件同规则自行做一次公开参照），把结果写入前提，然后才审阅。简单和中等跳过，直接审阅。建议路由在这次之后按事实重判。没有复杂档典型情况时可以低于初步档位。已经命中复杂档时不得降档。

## 审阅

本节各审阅环节对应 [references/state-machine.md](references/state-machine.md) 的「审阅收敛」「审阅未收敛」两个事件；走到审阅后按该网格查下一状态，与本节规则有出入时以本节为准。

写完方案（或接到上游方案）、改代码之前做一次。状态为 `执行中` 且出现新的决策点时再做一次。状态为 `已交接` 时，已交给下游的步骤不重写；出现新的决策点时再审。还有未核对的 P0 或 P1 时，只写入并核对尚未开始的步骤，不因完成程度改回 `已停`。

执行者写不出方案时，退出点用「理解不够」，到此为止。

方案里已经有线上动作、泄密、或未点名的危险操作：状态改为 `已停`，到此为止。

完成判据保持一条可检查的话。交付标准列出本任务应有的交付面要求，每条可检查。「不做的事」列出本任务排除的行为。复杂档的质量画像与显式降级按 [references/quality-profile.md](references/quality-profile.md) 检查字段是否齐全、底线能否验证、降级确认状态是否属实。这四处是审阅边界。

派审提示词原样贴上当前完成判据、「不做的事」，复杂档再贴上质量画像与显式降级原文，以及下表该环节的审与不审，并写明：返回完成程度（高、中、低）和范围内意见；有 P0 或 P1 时完成程度取中或低。再审再贴上上一轮每一条 P0 与 P1，要求逐条标已消失或仍在。只写「范围同前」的派审作废，改写提示词后才算一次审阅。

| 环节 | 审（初审） | 不审 | 意见可改 |
|------|----|------|----------|
| 步骤确定（写完方案到进入「写完之后」之前） | 这条完成判据能否检查；按现有步骤能否走到它；交付标准是否漏了任务应有的交付面、或列了超出任务所需的项；阻塞点、退出点是否会改道 | 架构、接口、schema、代码骨架；完成判据与「不做的事」都没有的新行为 | 这条判据的可检查写法，交付标准的增删改，或步骤的动作、要点、验证 |
| 执行中的新决策点 | 这一条岔路，以及它会改到的、尚未验证的步骤 | 已验证步骤；这条岔路碰不到的判据；详细设计 | 这条岔路影响到的、尚未验证的步骤 |
| 已交接后的新决策点 | 尚未开始的步骤，以及这一条岔路 | 已交给下游的步骤；下游账本里已勾掉的实现；详细设计 | 尚未开始的步骤 |

再审不重开上表。只核对待核对的 P0 与 P1，以及本轮写入直接造成、且仍在边界内的新 P0 或 P1。换一种写法仍指同一条判据、同一步或同一退出的，算仍在。

要新增完成判据与「不做的事」都没有的行为：不编号，不写入，不参与完成程度。改完成判据只为让同一结果变得可检查，写完仍是一条可检查的话。前提中的事实写错，且因此使现有步骤走不到这条判据：记为 P0 或 P1，写入前提或对应步骤。半屏里没写到的仓库细节，只有会让步骤走错或让判据不可检查时才编为 P0 或 P1。需要先定接口、架构或代码骨架才能判断：意见写「需要详细设计」，不编号、不给设计内容。执行者改为 `已停`，路由用「本流程不做详细设计」。

审阅者只读，不改工作区。一次审阅返回完成程度和范围内的改进意见。每条意见带 P0、P1 或 P2，写清改哪一条完成判据或步骤，并指回已有知识、已有方案或公开方案。完成程度写入方案的「方案置信度」。术语见 `CONTEXT.md`。

- **P0**：完成判据不可检查，或按步骤走不到判据，或漏了会改道的阻塞或退出；复杂档质量画像缺必要字段、或字段写成空泛形容词，也算。
- **P1**：验证对不住判据，或漏了任务应有的交付标准。
- **P2**：不改道的写法、顺序、两行限制或省略。P2 不参与完成程度，只写入坑，不改步骤正文。

完成程度的写入按显式条件判定，P0/P1 的有无优先于审阅者定级：

- 本轮发现含 P0 或 P1：完成程度取「中或低」。审阅者定级为高 → 写「中」；定级为中或低 → 从其值。
- 本轮无 P0 也无 P1：完成程度写「高」，审阅者定级不参与。

人选：评审者是必选项，每次审阅从三种里选一种，选中即唯一，不叠加。每次审阅的评审者记录到回复里（方式 + 具名角色 / Endpoint / 子 agent），可回看。

| 方式 | 何时选 | 怎么派 |
|------|--------|--------|
| role-based-reviewer | 复杂档的初审与执行中的新决策点（固定，不可替换）；goal 原文或当轮用户消息点名、写 `roles=`、或要求按岗位 / 多角色视角审 | 固定项与点名 `mode=review`：`mode=review`、`roles=product,design,engineer`；点名的 `mode=ask` 时 `roles` 用点名的，没点名由它按自己的门禁推断，不替它加角色 |
| agent-roster | goal 原文或当轮用户消息写了 `agent-roster` 或点名名册 Endpoint | 委托 `$agent-roster` 做名册审阅；点名唯一 Endpoint 走它的快速路径，只说用名册没点名谁时按它的 routing 选一个最匹配的直接派，不列候选表 |
| subagent | 前两条都不命中时的默认选择 | 宿主另起一个子 agent，按质量画像挑视角（无画像按默认）；宿主能分出更强模型时用更强的一档，给不出排序时用该宿主的最强档；当前模型已是最强档时，仍另起一个同模型子 agent，并在前提的事实里记「无更强档」 |

- 点名冲突时以当轮消息为准。简单和中等不强制三角色。
- role-based-reviewer 固定项：返回的分级发现映射：Blocker 记 P0，Major 记 P1，Minor / Suggestion 记 P2；完成程度按本节规则写入，不由它自定。读不到该 skill：状态改为 `已停`，退出点「审阅派不出」。goal 原文或当轮用户消息点名了其他审阅方式时以点名为准，不叠加。
- agent-roster：执行器不可用、证据不足、或还要人：状态改为 `已停`，退出点「审阅派不出」。
- subagent：起不来就换下一个可用模型，最多两次。两次都没有审阅结论：状态改为 `已停`，退出点「审阅没有结论」。
- 三选一选不出（都没被点名、且执行者也判不了该用哪种）：状态改为 `已停`，退出点「评审者未定」，路由写需要的指定。

执行者自己给出的完成程度不算审阅结论。

评审是否通过只看完成程度是否为高。只有完成程度、没有改进意见、也没有诚实结论：再叫一次审阅者。第二次仍没有：退出点「审阅没有结论」。

**核对**（本轮有 P0 或 P1 时）：

1. 把 P0 与 P1 写入完成判据或步骤，P2 写入坑。完成判据仍是同一结果的一条可检查的话。原判据不可检查、且意见给出仍描述同一结果的可检查句子时，用该句子替换。两条意见冲突时，采纳能让这条判据可检查的那条，另一条写入坑。路由写成 `完善中。核对本轮 P0/P1。此阶段不改代码。` 状态保持 `执行中`。然后做第一次核对。此阶段不改代码，不向用户索取「仍按此方案执行」或「按审阅建议改方案」。
2. 第一次核对：上轮每条都已消失，且没有点名本轮改动句与失效判据或退出的新 P0/P1 → 完成程度为高，收敛。某一条仍在（含只换写法）→ `已停`，退出点「审阅不通过」，不再写入。上轮都已消失，且新的 P0/P1 点名了改动的那一句以及失效的判据或退出 → 再写入一次，做第二次核对。点不出改动句或失效处的，不当作新的 P0/P1。
3. 第二次核对：这些新意见都已消失，且没有又冒出的 P0/P1 → 完成程度为高，收敛。仍有未消失的，或又冒出新的 → `已停`，退出点「审阅不通过」，不再写入。

本轮没有 P0 与 P1：P2 写入坑，完成程度为高，收敛，不再审。然后核对退出点，撞上就 `已停`，否则进入「写完之后」。

还有没核过的 P0 或 P1 时，完成程度为中或低也继续完善，不因此 `已停`。核过仍在才是「审阅不通过」。只剩 P2 不是这个结论。P0 或 P1 写不出改法时，先对照已有知识、已有方案、公开方案；简单和中等在还没对照过公开方案、且缺口可能被公开做法补上时，先对照再下结论。三处都补不上：`已停`，退出点「审阅不通过」，回复写明要达到的完成程度以及这三处为什么补不上。

用户在完善期间明确说「仍按此方案执行」：停完善，按当前已写下的步骤进入「写完之后」。不主动索取这句。不在收敛后把它列成选项。不把它解释成在本会话实施复杂档步骤。

进入「写完之后」：简单档改为 `执行中` 并接着做。中等档改为 `已交接`，按中等路由开工。复杂档改为 `已交接`，按复杂路由开工。三档都不询问路由。

## 旧方案

读到旧格式的 Goal 方案（缺「状态」、缺「方案置信度」、以「已达到预期」开工、或收敛后仍等「走 task-explore」）：按 [references/legacy-plans.md](references/legacy-plans.md) 迁移后续做。

## 写完之后

本节三档路由对应 [references/state-machine.md](references/state-machine.md) 的「判据成立」「步骤推进」等事件在「执行中」「已交接」行里的格子；网格只做索引，三档规则以本节为准。

只在评审收敛、退出点已再次核对之后，才进下面三档。档位判定按方案里的复杂度路由，不重判。

- **简单**：状态 `执行中`。路由写 `从第一个未验证步骤做到完成判据与交付标准，或退出点。` 同一轮接着做，允许随后改代码。
- **中等**：状态改为 `已交接`。同一轮开始衔接。路由固定为：`已交接。审阅者已经拷问过方案。直接 openspec-propose，再 openspec-apply-change。方案正文原样带入。进度只认该 change 的 tasks.md checkbox。全勾且完成判据成立才改为已完成。未完则下轮从第一个未勾项继续，不重出方案。`
- **复杂**：建议已在步骤里。同一轮不改业务代码。状态改为 `已交接`。同一轮开始衔接。路由固定为：`已交接。直接 task-explore，不向用户确认路由。slug 由 task-explore 推断，不另起任务名；new 时把完成判据、质量画像与显式降级原文快照、步骤、阻塞点、坑逐字登记进 TASK.md「方案」，作为 explore 的输入而非冻结结论。--goal 带上目标、完成判据和采纳方案。按 new → explore → design → decide → handoff 逐阶段推进，不跳阶段。创建目录、选阶段、确认冻结、脏工作区选择走「审阅」，不向用户列选项。审阅收敛则采纳推荐默认并继续，其中冻结即 `decide` 并 `handoff`。不在本会话按步骤改代码。进度只认 driver 的 tasks.md checkbox。全勾且完成判据成立才改为已完成。`

中等档在评审收敛时已经是 `已交接`，下一跳是 `openspec-propose`。复杂档在评审收敛时已经是 `已交接`，下一跳是 task-explore。handoff 之前路由是 task-explore 的当前阶段，handoff 之后是 driver 的第一个未勾项。

中等在 `已交接` 后发现已是项目级重构、逻辑重塑，或业务逻辑复杂且涉及面广：停止改代码，状态保持 `已交接`，路由换成复杂档那句，当轮开始 task-explore，不另问路由。

checkbox 全勾但完成判据不成立：状态改为 `已停`，不标完成。汇合时以本方案里的完成判据为准。

## 退出点

判定：

- **理解不够**：写不出一条可检查的完成判据，或步骤主体靠会改方案的猜测。执行者写方案时就能判定的，直接 `已停`。进入评审循环之后，写不出判据改由改进意见或诚实结论处理，不用这个标签代替循环。
- **审阅不通过**：按「审阅」节停：同一条 P0 或 P1 核过仍在，第二次核对仍有 P0 或 P1，或写不出改法。回复写明要达到的完成程度。只剩 P2、或还有没核过的 P0/P1，不是这个标签。
- **审阅派不出**：该走名册审阅时，执行器不可用、证据不足，或还要人；点名的审阅 skill 读不到也算。
- **审阅没有结论**：本机子 agent 换过一次后仍没有审阅结论。或者连续两次审阅只有完成程度、没有改进意见、也没有诚实结论。
- **评审者未定**：三种评审方式都没被点名，且执行者也判不了这次该用哪种。路由写需要的指定（方式 + 人选），等用户指定后再审。
- **降级未确认**：复杂档的显式降级仍有 `pending`。状态改为 `已停`，路由写「需要用户确认降级表」，不开工、不交接。停止回复逐条列出 `pending` 降级（维度、默认期望、实际交付、偏差理由），并逐条给出「接受 / 不接受」推荐意见；降级使完成判据不成立时，按判据不成立停止并报诚实结论，不空转等待。只有用户点名接受该项、或明确说按降级表全部确认时，才把该项改为 `confirmed` 并继续；审阅收敛与单独的「继续」都不算确认。实现中发现新的降级，补进降级表后同样停在这里。
- **阻塞解不开**：有当轮解除不了的阻塞点。
- **未点名的危险操作**：任务描述没点名这些动作就停：破坏性 git、删除或不可逆改写、改密钥或权限、对外发送、不可逆迁移。点名了就做。
- **线上动作**：一律停，任务描述里写过也停。范围：直接改线上数据，以及生产、预发、共享远程上的合入、打 tag、推默认分支、部署。每一步单独要授权。
- **同一验证连败两次**：同一条验证连续失败两次，且没有新事实。
- **泄密**：密钥、令牌、内部 URL 或公司代码要写进公开仓库。始终停。
- **执行中升档**：开工后发现已是中等或复杂。立刻停止改代码。已经改过的可逆部分留在工作区，退出说明里写清，不自动回滚。状态改为 `已交接`，路由换成「写完之后」里对应档位的交接句，当轮开始衔接，不另问路由。

同时撞上多条时一次说清。除执行中升档外，命中后状态改为 `已停`，路由写成需要的授权，不把 goal 标成完成。`已交接` 期间命中除执行中升档外的退出点，同样改回 `已停`。执行中升档改为 `已交接` 并按新档位衔接。

各退出点对应的「退出点命中」事件在 [references/state-machine.md](references/state-machine.md) 已停行的格子里登记；网格只做索引，判定与文案以本节为准。

## 授权

授权只用于退出点已经点名的动作。评审收敛后的档位路由不另要授权。单独的「继续」只在因退出点而 `已停` 时重申仍停，不新增工作，也不挡住已收敛的档位路由。

授权项是封闭集合，等于退出点已列出的那些，不发明新授权项。「报使用者裁决」「停下等用户确认」的停下形状是：写明事实、推荐意见与需要的一句话决定；协议级等待（待裁决、待确认）是状态不是任务，不登记进任务清单，命中即在同轮回复呈现。

撞上退出点后不新增工作，不把 goal 标成完成。回复写明退出点和需要的授权。下一轮仍没有授权，就只重申这个状态。不得把重申写成「请回复其一」。

goal 自动续跑（续跑提示来自 goal 系统而非用户回复）既不是授权，也不是用户「继续」：已停期间允许且应做只读环境查证、外部原文取证与证据固化——这些不产生交付物，不属于上一句的「新增工作」；禁止写交付代码、改完成判据/步骤/降级表、commit/push/部署。同一退出点被自动续跑连续第三次且仍无用户输入时，标记 goal blocked 并给出交接摘要（已完成、未完成、证据、下一步），不再第四次重申。blocked 是「已停」的交接形态，不是第五状态。重申与 blocked 交接均不得写成选项列表。

**无进展轮（兜底）**：状态与退出点与上一轮完全相同、且本轮没有带来新的外部输入（用户消息、审阅结论、环境新事实均不算）时，禁止原样重复上一轮回复。输入形态在 [references/state-machine.md](references/state-machine.md) 已停行有格的按格走；无格的做本节列名的只读工作，无可做的只读工作时按 goal 自动续跑第 3 次处理：标记 blocked 并给出交接摘要，不再原样重申。执行中或已交接出现无进展轮时，视为协议异常，状态改已停，路由写「无进展轮兜底触发」。

## 执行中改步骤

离开完善之后：完成判据不变、状态仍是 `执行中`、档位仍是简单、没撞上其他退出点时，在后续回复里改正步骤，按新步骤继续。完成判据要改、升档、或撞上其他退出点：停。完善期间的改正不受本段限制。

## 做完

状态改为 `已完成` 才算做完。`handed-off` 与 propose 完都不算。简单档在完成判据成立且交付标准全过时做完。中等与复杂在 checkbox 全勾、完成判据成立且交付标准全过时做完。交付标准写「无」时只看完成判据。复杂档还要求质量画像字段齐全、`pending` 降级数为 0，且 `confirmed` 降级在验证记录里可追踪；不满足不标完成。停止新增工作，回复里对照判据说明已完成。环境能把 goal 标成完成就标；不能标时，回复仍须对照判据宣布已完成。退出点不标完成。

## Self-evolution

本 Skill 具备经验积累、评估与持续进化能力。目录（均相对本 Skill 根目录）：

```text
skills/task-goal/
├── SKILL.md
├── examples/      # 经过验证的优秀执行案例
├── evals/         # 可验证成功标准
└── experience/    # 真实失败 / 成功 / 规律
```

不要为了自进化而破坏上文已规定的目标、流程、工具用法、输出与约束。

### Examples

执行复杂任务前：

1. 检查 `examples/`
2. 找到与当前任务相关的成功案例
3. 优先复用已经验证的方法

没有相关案例时按上文正常执行，不要编造案例。

### Evaluation

任务完成前：

1. 检查相关 `evals/`
2. 验证关键输出
3. 检查是否违反 Skill 约束
4. 尽可能运行相关 Eval Cases（见 `evals/cases.yaml`）

优先确定性 Eval；无法确定性判断时再用 LLM Judge。Eval 失败则先修输出，不要带着失败交卷。

### Experience

任务完成后，出现以下情况才写入 `experience/`：

- 失败
- 用户纠正
- 明显成功
- 新的有效执行方法
- 可复用的经验

不要记录 trivial information。不要伪造条目。密钥、内部 URL、凭据不得写入。

单次失败 → `experience/failures/`。重复出现的规律 → `experience/patterns/`（至少两次同类证据）。

### Evolution

只有当 Experience 暴露出**可复用、稳定的问题或模式**时，才考虑修改本 Skill。

遵循：

```text
Experience
    ↓
Repeated Pattern
    ↓
Improvement Proposal
    ↓
Eval
    ↓
Pass
    ↓
Update Skill
```

禁止：

```text
Single Failure
    ↓
Directly modify SKILL.md
```

进入 Skill 正文的 Experience 必须同时满足：可复用于多个类似任务、有足够证据、能明确改善结果、不破坏已有能力、可通过 Eval 验证。一次性特殊情况只留 Experience，不改 Skill。

实际更新生产 `SKILL.md` 时：

1. 不要直接覆盖原文；记录 version / change / reason / evidence / evaluation。有 Git 则优先靠 Git diff 留历史。
2. 若改动来自**真实执行经验**：优先委托 `skill-evolver`（`evolutions/` → 验证 → 晋升），不要本 Skill 自己改生产稿。
3. 若只是结构/规则的显式修订且环境有 `skill-upgrader`：走其 `update` 模式（`<skill-dir>/patches/`），仍须先提案再应用。
4. 未展示 Proposal 并获得用户确认前，不改生产 Skill。
