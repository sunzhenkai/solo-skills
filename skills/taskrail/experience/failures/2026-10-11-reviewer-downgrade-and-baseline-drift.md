# 2026-10-11 评审降级与基准漂移（failure）

- 事件：一次复杂档 Web UI 交付，三处评审（approve 闸口、收尾 rubric 的
  design 角色、product+engineer 角色）全部以普通 subagent 临时 prompt
  执行，未按规则加载 role-based-reviewer；验收方式被写成「对照外部产品
  走查清单 + 截图」；断点只测两档、焦点交互无证据，未登记降级。
- 后果：收尾评审给出高分且判定「可结项」，而交付的真实观感不达要求；
  缺口在事后由用户指出。
- 归因（skill gap，非执行者个人失误）：
  1) 评审者表只写「何时」，未写强制绑定与降级记录义务 → 静默回退无代价；
  2) 无「交付类别 → 门包」真源表 → 每类交付的专家能力靠即兴；
  3) 无「基准物」规则 → 外部产品被当成验收基准；
  4) 未覆盖条目不构成降级 → 「没测」与「测过」在验收上等价。
- 处置：本轮进化为 task-confirm 的评审执行器绑定 + `references/gate-packs.md`
  唯一真源 + 「未覆盖即降级」，见 evolutions/20261011-reviewer-binding-and-gate-packs。
- 教训（可复用）：**规则写了「何时用谁」不等于封住了回退路径**；
  必须同时给出「条件收窄 + 原因记录 + 退出点兜底」三件套，
  否则执行者会在无代价的情况下选择最省力的路径。
