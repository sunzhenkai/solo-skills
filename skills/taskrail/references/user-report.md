# 对用户说话（task 系列唯一出处）

taskrail / task-intent / task-explore / taskflow 凡是直接给用户看的话都按本文件：复述、resume、进度、问题报告、闸口、停下等用户、完成通知、评审摘要。落盘文件（`TASK.md`、driver、验证记录、评审文件）可以保持结构化。

## 1. 先说影响和要改什么

第一句讲什么坏了 / 对谁有什么影响、打算改什么。白话、第一人称、完整句子，像同事说话；不以根因推导、文件名、行号、函数名开头。

## 2. 问题报告的顺序

1. **影响面**：哪些功能 / 环境 / 人受影响。
2. **要改哪些地方**：按模块或行为说，不按文件名。
3. **怎么改**：每处一两句。
4. **我的决定**：有取舍就按推荐定下，陈述句带一句理由。

## 3. 内部词留在台账

phase、status、tier、driver 名、change id、checkbox 编号与计数、门名、digest、criterion、slice、OpenSpec 等只写进台账，用户问起再给；非用不可时带一句白话。不倒「字段：值」清单，不转贴术语表、工具过程或读过的文件清单。file:line 只放结尾「细节（可跳过）」一行，最多 3 条。

## 4. 先查资料，能查到的不问

先读一手资料再开口；能从代码、配置、文档、历史任务里查到的，不写成假设、不拿去问用户。用户纠正后先回资料重查，再带出处说改了什么。

## 5. 说决定，不提问

本节是 task 系列「不提问」的唯一真源，别处只指针到这里。

1. **默认陈述**：有歧义或取舍就按推荐定下，用陈述句说决定和一句理由；不用问号，不写「要不要」「你看行吗」「对吗」，不加「理解偏了请纠正」这类结尾邀请。
2. **真阻塞才停**：删除或迁移数据、改共享配置（别人也在用的环境、CI、共享库配置）、线上 / 不可逆 / 对外发送、要改完成判据、缺凭据或只有用户知道的信息（账号、权限、外部事实）。停时也用陈述句说清停在哪、需要什么。
3. **难回头单独说**：数据结构、接口 / API 形状、库表 schema、存储格式、对外命名、选用的依赖、会删或迁数据的做法——不停下，但在复述 / 进度 / 完成通知里单独一行「我定了 X，因为 Y」。

- 记账（建任务、恢复、起名、建 `tasks/`、更新台账、勾 checkbox、重建 INDEX）直接做，一句话说出决定。
- 普通可回头取舍（命名、布局、组件怎么拆、先做哪步）直接定，一句话带过。
- 所有决定追加到 `TASK.md`「已做决定」（决定 / 理由 / 可逆 / 来源阶段）；完成通知最后一句指向它。

## 6. resume / 停下时的四行

恢复任务、或因真阻塞停下时，用这四行（没有的行省略）：

```
这个任务是要 <目标白话>。
目前 <做到哪了，用结果说>。
还卡着 <影响 + 原因>，需要你 <只在真阻塞时写，说清要什么>。
接下来我会 <下一步动作，白话>。
```

有难回头的决定时，另起一行「我定了 X，因为 Y」。

## 7. 发出前自检

第一段不应出现：`phase` / `status` / `tier` / `-driver` / 「x.y 未勾」/ `*.py:行号` / 命令名当下一步（如「进 apply」）/ 记账类问题 / 以问号结尾的提问（真阻塞除外）。

## 前后对比

- 问题报告 —— 前：「根因：adapters.py:213 的 fetch-ref stub 致 ref-drift fail-closed；phase propose；1.1 未勾；要不要更新 TASK.md？」；后：「发布时拿到的版本引用和实际 tag 对不上，所以发布被拦下。要改两处：解析版本引用的那一层、环境选择逻辑。修法是按 tag 精确取引用，取不到就明确报错。我定了直接改配置名、不加兼容层，因为留两套名字更难维护。」
- resume —— 前：「目标 X / phase apply / 未决 2 / 建议下一步：进 apply」；后：「这个任务是要把导出提速。目前方案已经定了，第一部分已实现。接下来我会做剩下的部分。」
- 停下 —— 前：「等待项 → 仍未解除」；后：「还卡在测试环境的权限上，没法验证发布，需要你开通测试环境的部署权限。接下来我会在权限到位后接着跑。」
