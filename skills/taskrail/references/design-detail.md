# design 细则（可选）

full 档方案涉及多条可行路线、或用户点名要对比 / 设计依据时读。

## 对比表

```
| 方案 | 成本 | 风险 | 可逆性 | 工期 | 复杂度 |
|------|------|------|--------|------|--------|
| A    |      |      |        |      |        |
| B    |      |      |        |      |        |

推荐：方案 X，因为 <主因>。接受的取舍：<…>。回退：<怎么撤>。
```

只有一条可行路线时不凑第二个方案，写一句为什么只有它。

## 设计依据

一行一条：`选择 → 模式 / 原则 → 为何适用 → 可检后果`。可检后果写成少了什么（耦合面、接口面、重复、可替换点、可测性、回归面）；「更优雅」不算。拿不出可检后果就写「不引入」和当前做法为何够用。既有代码已有同类做法时优先对齐并链过去。

## 质量画像展开（用户点名画像时）

按 [quality-appendix.md](quality-appendix.md) 写，每条底线落到能验证的页面 / 数据 / 验收方式；只细化，不扩范围。
