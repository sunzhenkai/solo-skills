# 确认协议（薄）

闸口（wizard 定稿、design 定稿、approve、危险动作前）只回答「放行 / 改后放行 / 停」。怎么说话见 [user-report.md](user-report.md)，本文不重复。

## 两种模式

| | human（默认） | goal（消息含 `/goal` 或 `goal:`，或被上游以 goal 委派） |
|---|---|---|
| 闸口 | 把推荐写成已定的决定（带一句理由）给用户看，用户说「继续」或指出要改哪条后放行；定下的追加到「已做决定」 | 不问人：写推荐 → 派另一个模型审 → 收敛即放行，同轮继续 |
| 真阻塞 | 停，陈述需要什么 | 同左；审阅收敛不放行真阻塞 |

真阻塞清单只在 [user-report.md](user-report.md) 第 5 节。用户没回话不算确认；单独「继续」不算对真阻塞动作的授权，要用户点名该动作。

## 闸口前自查

呈现前自己走一遍：判据可检查；步骤从现状走得到判据；没有漏掉或越界的交付标准。不过就先改方案，不把自查失败包装成待确认项。

## goal 的另一个模型审（短规则）

- 审阅者用与执行者不同、最好更强的模型（`model=` 或 agent-roster `endpoint=`）；派不出时写明原因，主会话按同一清单自审并把结论标「把握低」。
- 随附：`criterion`、「不做」、要审的方案或步骤；写明只审「判据可检查、步骤走得到判据、交付标准有无漏 / 越界」，不审架构与代码细节。
- 返回 P0（判据不可检查或走不到判据）/ P1（验证对不上判据、漏交付标准）/ P2（写法问题，不挡路）。无 P0 / P1 即收敛。
- 有 P0 / P1 就改了再审；同一条连续两轮还在，或同一验证连败两次，停下按 user-report 四行说卡在哪。
