# 确认协议（薄）

闸口只回答「放行 / 改后放行 / 停」。怎么说话见 [user-report.md](user-report.md)，本文不重复。

## 停点（human 与 goal 在闸口上的差别只在这张表）

| 时机 | human（默认） | goal（消息含 `/goal` 或 `goal:`，或 `TASK.md.confirm_mode: goal`） |
|---|---|---|
| wizard 定稿：意图复述 + plan 要点（判据、步骤、档位；拆了再加路线图，一行一项）在同一条消息里说 | 停，等用户说对或指出要改哪条 | 另一个模型审意图与 plan，收敛即同轮继续 |
| approve（仅 full 档） | 停，用户说「继续」即放行，同轮冻结并 handoff | 另一个模型审，收敛即同轮冻结并 handoff |
| 子任务的 wizard 与 approve（没超出父任务路线图那一行的范围和子判据） | 说决定，接着做 | 同左 |
| 观感验收（用户原话有观感目标时） | 评审过后给用户看改前 / 改后截图，用户说可以才完成 | 另一个模型审截图，自己迭代 |
| 其余阶段切换（design、apply、archive）、片间检查点、子任务之间 | 说决定，接着做 | 同左 |
| 真阻塞 / 卡住（[user-report.md](user-report.md) 第 5 节） | 停，陈述需要什么 | 同左；审阅收敛不放行真阻塞 |

用户没回话不算确认；单独「继续」不算对真阻塞动作的授权，要用户点名该动作。委托出去的 stock `openspec-*` 自带的停顿与提问不算停点，由编排者按 taskflow「经 taskrail 委托时」代答。

## 闸口前自查

呈现前自己走一遍：判据可检查；步骤从现状走得到判据；没有漏掉或越界的交付标准；拆了的，子判据合起来覆盖总判据、彼此不重叠、依赖无环。不过就先改方案，再呈现。

## 另一个模型审（goal 闸口、goal 意图、观感验收共用）

- 审阅者用与执行者不同、最好更强的模型（`model=` 或 agent-roster `endpoint=`）。经 `role-based-reviewer` 派审时它报派不出，由本协议接手：写明原因，主会话按同一清单自审，结论标「把握低」。
- 随附：`criterion`、「不做」、要审的方案或步骤。意图审另附用户原话、复述、探索摘要，清单用 [intent.md](intent.md) 第 5 节；闸口审只看「判据可检查、步骤走得到判据、交付标准有无漏 / 越界」，有路线图再看「子判据合起来覆盖总判据、彼此不重叠、依赖无环」，架构与代码细节留给实现阶段的评审。
- 严重级：P0（= Blocker）判据不可检查或走不到判据（子判据覆盖不了总判据、依赖成环都算）；P1（= Major）验证对不上判据、漏交付标准、子判据重叠；P2 写法问题，不挡路。无 P0 / P1 即收敛。
- 有 P0 / P1 就改了再审；观感验收的收敛与停止以 pretty-ui `references/critique.md`「迭代与停止」为准。闸口审同一条两轮还在，按 user-report 第 5 节「卡住」停；意图审两轮不过按 intent.md 第 5 节记 `assumed` 继续。
